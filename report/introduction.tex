\section{Background and Objectives}

Proving Program Equivalence is the act of verifying that, for any input, two programs always give the same output. This can be formally defined using Hoare Triples: two programs \(C_1\) and \(C_2\) are equivalent if, for arbitrary precondition \(P\) and postcondition \(Q\): \[ \models \{P\}C_1\{Q\} \iff \models \{P\}C_2\{Q\} \]

If this can be proven, then these programs are equivalent; one of these programs can be substituted for the other without affecting the behaviour of the overall system. This has applications in a variety of fields. For example, compiler developers can use this to ensure that optimisations always preserve the intended behaviour of the original program.

Therefore, Program Equivalence is a very exciting area of Computer Science. However, it is a very difficult task, especially since the problem is undecidable in general. To mitigate this problem, a variety of tools are being developed to help prove equivalence automatically \parencite{leinoDafnyAutomaticProgram2010,lahiriSYMDIFFLanguageAgnosticSemantic2012,IntroductionStainless091,cadarKLEEUnassistedAutomatic}. These tools can make proving equivalence significantly easier for developers, especially when working with large codebases. They can also generate counterexamples when equivalence cannot be proven, making debugging much easier. The main drawback of these tools is that, in general, they still require a significant level of user assistance to complete proofs, often involving writing complicated specifications, loop invariants or auxiliary lemmas. The average software developer will not have the necessary expertise to provide these, thus, these tools will be inaccessible to them.

Therefore, the general aim of this project is to build a new tool, learning from the current state-of-the-art tools, that decreases the level of user assistance required as much as possible, thus allowing the average software developer to better reap the benefits of using program equivalence tools in their work. In particular, the main objectives of this project are as follows:

\begin{description}
    \item[\nameref{sec:tools-desc}] To describe the current state-of-the-art tools for proving program equivalence
    \item[\nameref{sec:audit}] To explore Dafny's capabilities in proving program equivalence
    \item[\nameref{chp:design}] To implement a tool on top of the Dafny verifier that will allow the user to prove the equivalence of two Dafny functions with as little user assistance as possible
    \item[\nameref{chp:evaluation}] To evaluate this tool against the current state-of-the-art tools
\end{description}

After describing the current state-of-the-art tools, this project will focus solely on the Dafny program verifier. Dafny is a popular tool under active development by Amazon \parencite{leinoDafnyAutomaticProgram2010}, therefore, building a tool on Dafny would be highly relevant to modern software engineering projects. This is especially true since Dafny can be compiled into a variety of popular languages, including C\#, Java and Python, allowing verified code to easily be integrated into existing codebases. 

To find an understanding of Dafny's capabilities, I used the set of program equivalence tests in the GitHub repository for the Stainless Scala verification tool \parencite{StainlessFrontendsBenchmarks}. After converting them from Scala to Dafny I attempted to prove equivalence for each pair of functions. Using this I identified a number of challenges Dafny encounters. One of the main challenges involved generating equivalence lemmas for helper functions, and calling them with the correct arguments and under the correct conditions. Since the Dafny verifier often proves lemmas through induction, further challenges included the verifier often requiring a variant to prove termination, and sometimes requiring an explicit statement of the induction scheme. An example that demonstrates all three of these challenges is as follows. Here are two functions called \lstinline|insertRandomSortedM| and \lstinline|insertRandomSorted1| that each generate a specified number of random numbers, and insert them into a sorted list while maintaining its order.

\begin{lstlisting}[caption=\lstinline|insertRandomSortedM| and \lstinline|insertRandomSorted1| Functions]
function insertRandomSortedM<Seed>(seed: Seed, next: Seed -> (Seed, int), count: int, xs: List<int>): List<int>
  {
  if (count <= 0) then xs
  else
    var (nxtS, t) := next(seed);
    insertRandomSortedM(nxtS, next, count - 1, insertM(xs, t))
}

function insertRandomSorted1<Seed>(seed: Seed, next: Seed -> (Seed, int), xs: List<int>, count: int): List<int>
  decreases count {
  if (count <= 0) then xs
  else
    var (nxtS, t) := next(seed);
    insertRandomSorted1(nxtS, next, insert1(t, xs), count - 1)
}
\end{lstlisting}
%
In both functions, the parameter `seed' is the current random generation seed, `next' is the random generation function outputting the next seed and the generated number, `count' is the number of random numbers to generate and `xs' is the current sorted list. Each function uses a helper function called \lstinline|insertM| and \lstinline|insert1| respectively to insert a single number into a sorted list while maintaining its order:

\begin{lstlisting}[caption=\lstinline|insertM| and \lstinline|insert1| Functions,label=lst:insertM-insert1-functions]
function insertM(xs: List<int>, t: int): List<int>
  decreases xs {
  match xs {
    case Nil => Cons(t, Nil)
    case Cons(hd, tl) =>
      if (t <= hd) then Cons(t, xs)
      else Cons(hd, insertM(tl, t))
  }
}

function insert1(t: int, xs: List<int>): List<int>
  decreases xs {
  match xs {
    case Nil => Cons(t, Nil)
    case Cons(hd, tl) =>
      if (t <= hd) then Cons(t, xs)
      else Cons(hd, insert1(t, tl))
  }
}
\end{lstlisting}
%

The Dafny verifier requires the following lemmas to prove the equivalence of \lstinline|insertRandomSortedM| and \lstinline|insertRandomSorted1|:

\begin{lstlisting}[caption=Equivalence Lemmas for \lstinline|insertRandomSortedM| and \lstinline|insertRandomSorted1| Functions]
lemma equivalenceInsert(t: int, xs: List<int>)
  ensures (insert1(t, xs) == insertM(xs, t))
{}

lemma equivalenceInsertRandomSorted<Seed>(seed: Seed, next: Seed -> (Seed, int), xs: List<int>, count: int)
  ensures (insertRandomSorted1(seed, next, xs, count) == insertRandomSortedM(seed, next, count, xs))
  decreases count
{
  if count > 0 {
    var (nxtS, t) := next(seed);
    equivalenceInsertRandomSorted(nxtS, next, insert1(t, xs), count - 1);
    equivalenceInsert(t, xs);
  }
}
\end{lstlisting}

\section{Implementation and Evaluation}

The aim of this project is to implement a tool to address the challenges identified above. In particular, the main contributions of this project are as follows:

\begin{description}
    \item[Dataset of Equivalence tests] The conversion of Stainless tests into a dataset of pairs of equivalent Dafny functions
    \item[Novel Algorithm] Development of the Function Merging algorithm to automatically generate equivalence lemmas 
    \item[Tool] Implemented EquiDafny: a command-line tool that implements this algorithm
    \item[Evaluation] An evaluation of EquiDafny against the Dafny verifier and the Stainless equivalence checker
\end{description}

The main algorithm EquiDafny uses is called `Function Merging'. By exploiting similarities between the structures of function bodies, these structures can been split into their constituent parts and recursively `merged' together. This algorithm has two outputs. The first is a set of mappings between the parameters of one of the functions to the parameters of the other. These mappings describe which parameters have the same purpose across the two functions. These mappings are used to ensure arguments are inserted correctly into the function calls within the postconditions of each lemma. The second output is the body of each lemma. This includes variable declarations and calls to any equivalence lemmas with the correct arguments and under the correct conditions.

EquiDafny is implemented in Scala. The tool is called by passing in a single JSON configuration file. This file provides any important details EquiDafny needs to run, including the names of the functions to be compared and a path to a single Dafny file containing all necessary source code. EquiDafny is split into several components including parsing, translation and formatting. The parsing component parses the initial Dafny source file (implemented using the Parsley parser combinator library \parencite{willisJmie6Parsley2026}). The translation component converts the data structure outputted by the parser into a structure that is easier to work with. Finally, the formatting component outputs the final equivalence lemmas to a file so that they can be checked by the Dafny verifier.
