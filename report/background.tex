\subsection{Dafny}\label{sec:dafny}

Dafny is a popular program verifier, under active development by Amazon~\cite{leinoDafnyAutomaticProgram2010}. It is primarily a programming language, containing many of the classic language features and constructs we expect from a modern programming language. However, in addition to this, it includes specification constructs, such as preconditions, postconditions and loop invariants. This allows Dafny's verifier to automatically prove theorems and that programs match their specifications. Dafny programs can also be compiled into a variety of other languages, including C\#, Java and Python, but only after Dafny has verified them. This allows verified programs to be integrated easily into existing codebases, without breaking any functionality.

Dafny's program verification heavily relies on Boogie~\cite{10.1007/11804192_17}, another state-of-the-art program verifier. The verification process involves translating a Dafny program into a Boogie program; this is then translated into a series of verification conditions, which are passed to the Z3 SMT solver~\cite{10.1007/978-3-540-78800-3_24}. 

Consider the following example, converted from the original Scala provided by \textcite{milovancevicProvingDisprovingEquivalence2023}. These two functions attempt to find the maximum element of a sequence of integers. The first is as follows:
%
\begin{dafny}
function maxR(l: seq<int>): int
{
  if |l| == 0 then -1
  else if |l| == 1 then l[0]
  else
    var m := maxR(l[1..]);
    if l[0] > m then l[0] else m
}
\end{dafny}
%
The second is as follows:
\begin{dafny}
function maxC(l: seq<int>): int
  decreases |l|
{
  if |l| == 0 then -1
  else if |l| == 1 then l[0]
  else
    if l[0] > l[1] then
      maxC([l[0]] + l[2..])
    else
      maxC(l[1..])
}
\end{dafny}
%
The main difficulty with proving the equivalence of these two functions is that they approach the problem in opposite ways: the first function processes the list from the end to the start, while the second processes it from the start to the end. However, despite this, Dafny is able to prove equivalence with almost no help from the user using this lemma:
\begin{dafny}
lemma maxEquivalence(l: seq<int>)
  ensures maxC(l) == maxR(l)
  decreases |l|
{}
\end{dafny}
%
This lemma states that, for any sequence of integers \dafnyinline{l}, the function calls \dafnyinline{maxC(l)} and \dafnyinline{maxR(l)} return the same output. Therefore, by proving this lemma, Dafny can prove that these functions are equivalent. However, in this case, Dafny requires the user to explicitly provide the length of the sequence \dafnyinline{l} as a variant to prove termination (this lemma is proven using induction).

For this example, the Boogie translation resulted in a file almost 3350 lines long. It begins with a series of type definitions and axioms, followed by the translation of each Dafny function, and ends with the translation of the equivalence lemma, taking only around 50 lines of code. Therefore, the Dafny programming language is highly expressive, allowing users to define functions in a concise manner. Meanwhile, the Dafny program verifier is capable of proving function equivalence, but it sometimes requires user assistance.

\subsection{SymDiff}

SymDiff is a differential program verifier \parencite{lahiriSYMDIFFLanguageAgnosticSemantic2012}. The system works by combining the two programs being compared into a single program called a `product program'. This product program contains the bodies of the individual programs to simulate both of their executions. Symdiff attempts to prove postconditions on this product program to verify the relationship between the individual functions. These postconditions are called `mutual summaries'. The postconditions can be proven by passing the product program to the Boogie program verifier.

An example of this process is demonstrated below~\parencite{lahiriAutomatedDifferentialProgramb}. Here is a method \boogieinline{F1} which adds to the global variable \boogieinline{g1} every integer from the initial value passed into the \boogieinline{F1} method to 100. \boogieinline{F1} is called from the \boogieinline{Main1} method with the initial value 0:
\begin{boogie}
var g1: int;
procedure F1(x1: int)
  modifies g1;
{
  if (x1 < 100) {
    g1 := g1 + x1;
    call F1(x1 + 1);
  }
}

procedure Main1()
  modifies g1;
{
  call F1(0);
}
\end{boogie}
%
Here is the method \boogieinline{F2} which instead adds double of every integer from the initial value to 100. It is called from the \boogieinline{Main2} method in the same way as above:
\begin{boogie}
var g2: int;
procedure F2(x2: int)
  modifies g2;
{
  if (x2 < 100) {
    g2 := g2 + 2*x2;
    call F2(x2 + 1);
  }
}

procedure Main2()
  modifies g2;
{
  call F2(0);
}
\end{boogie}
%
If \boogieinline{g1} and \boogieinline{g2} have the same initial value, after running \boogieinline{Main1} and \boogieinline{Main2}, then \boogieinline{g1} \(\leq\) \boogieinline{g2}. Thus, Symdiff can create the following product program:

\begin{boogie}
procedure MS_Main1_Main2()
  modifies g1, g2;
  requires g1 == g2;
  ensures g1 <= g2;
{
...
}
\end{boogie}
%
Since this process is very general, it is not limited to program equivalence. For example, SymDiff can be used in Approximate Computing, as described in \textcite{lahiriAutomatedDifferentialProgramb}. This is where you trade off the accuracy of a program (in an acceptable manner) for improvements in performance or energy consumption.

\subsection{Stainless}

Stainless is a verification framework that verifies that Scala programs obey their specifications \parencite{IntroductionStainless091}; when these specifications are violated, Stainless is able to provide counterexamples. For example, here is an implementation of a function to return the maximum of two integers~\parencite{piskacProceedings21stConference2021}. This property is enforced by the function's postcondition:
\begin{minted}{scala}
def max(x: Int, y: Int): Int = {
    val d = x - y
    if (d > 0) x
    else y
} ensuring(res => x <= res && y <= res && (res == x || res == y))
\end{minted}
%
However, this function is incorrect due to subtraction overflow when calculating \mintinline{scala}|d|. Stainless can identify this and provides several counterexamples, for example, when \mintinline{scala}|x = 0| and \mintinline{scala}|y = -2147483648|. This can be fixed by changing the types of \mintinline{scala}|x| and \mintinline{scala}|y| to \mintinline{scala}|BigInt|. After this, Stainless confirms that the postcondition is now correct. 
Stainless performs these verifications by passing each part of the program through a series of transformations, until it can be used by the Inox solver \parencite{EpfllaraInox2026}. However, an important restriction of Stainless is that it only supports a subset of Scala's features. This subset only includes the functional paradigm; the full description is in the Stainless documentation. The Stainless developers called this subset `Pure Scala'.

One part of Stainless's functionality that is especially relevant to this work is its equivalence checker \parencite{IntroductionStainless091,milovancevicProvingDisprovingEquivalence2023}. The abilities of this system will be a great inspiration for the rest of this project. In particular, its ability to automatically generate and prove equivalence lemmas for helper functions is especially important, as this is the main contribution EquiDafny should provide. 

Consider the following example, taken from the equivalence tests in Stainless's GitHub repository \parencite{StainlessFrontendsBenchmarks}. This is also an example used by \textcite{milovancevicProvingDisprovingEquivalence2023}, which I converted to Dafny in \Cref{sec:dafny}:

\begin{minted}{scala}
def maxR(lst: List[Int]): Int = {
    lst match {
        case Nil()           => -1
        case Cons(hd, Nil()) => hd
        case Cons(hd, tl)    => 
        if (hd > maxR(tl)) hd 
        else maxR(tl)
    }
} 

def maxC(l: List[Int]): Int = {
    l match {
        case Nil()                => -1
        case Cons(a, Nil())       => a
        case Cons(a, Cons(b, tl)) => 
        if (a > b) maxC(a :: tl) 
        else maxC(b :: tl)
    }
}
\end{minted}
%
Stainless is able to prove the equivalence of these functions fully automatically. Therefore, its abilities will be a great inspiration for this project. 

\subsection{KLEE}

KLEE is a symbolic execution engine that automatically generates high coverage test sets \parencite{cadarKLEEUnassistedAutomatic,ozkanKLEESmarterTest2025}. KLEE achieves this generation by simulating program execution with symbolic inputs, to explore every possible execution path a program can take. For example, here is an implementation of the \dafnyinline{sign} function. This example was taken from the KLEE tutorial \parencite{TutorialOneKLEE}:
\begin{minted}{c}
int sign(int x) {
  if (x == 0)
    return 0;
  if (x < 0)
    return -1;
  else
    return 1;
}
\end{minted}
%

This function can now be called with a KLEE symbolic variable as argument:
\begin{minted}{c}
int main() {
  int a;
  klee_make_symbolic(&a, sizeof(a), "a");
  return sign(a);
}
\end{minted}
%

Since there are three different paths through the \dafnyinline{sign} function (for each of the cases where \(x < 0\), \(x = 0\) and \(x > 0\) respectively), running KLEE on this program generates three test cases, one for each path respectively. 

For each path it explores, KLEE maintains the set of conditions needed for that path to have been taken, thus, if the path ends in an error, KLEE can use those conditions to generate a single test case that will create the error. Therefore, KLEE is a powerful tool, however, one of its main limitations is that the number of possible paths to keep track of can grow exponentially large when it is working with programs containing many loops and branches.

\section{Dafny: Technical Audit}\label{sec:audit}

There are many cases where the user needs to provide assistance to Dafny in order to prove equivalence. In this section, I will provide a series of examples to demonstrate where Dafny's limitations are in this area, and how the user can provide assistance to allow Dafny to overcome these challenges and prove equivalence. These challenges include a series of problems when generating and proving auxiliary lemmas, problems with proving termination of the equivalence lemmas in the presense of termination proofs for the individual functions, and problems with proving the equivalence of Dafny methods with imperative features, such as loops.

The majority of the following examples have been taken from the program equivalence tests in the GitHub repository for the Stainless Scala verification tool \parencite{StainlessFrontendsBenchmarks}. I converted all of their tests into Dafny functions, and proved their equivalence. Many of these tests consisted of more than 2 functions, each in their own file. For these cases, I concatenated all of these functions into a single Dafny file to form a single test, and proved the equivalence of each function with a single function, thus proving, through the transitivity of equivalence, that all of these functions were pairwise equivalent. This resulted in a total of 53 tests.

These tests cover a great variety of types of programs. The number of lines of code in each test ranges from around 10 to around 150. They cover a variety of inbuilt and custom data structures, including sequences, lists and the Option datatype. Some tests also cover concepts such as mutual recursion, generic types and higher-order functions.

Using these tests, I have attempted to characterise the cases where Dafny required user assistance. In this way, I have identified 7 different types of challenges. The following paragraphs describe what each type of challenge involves.

\paragraph{\nameref{sec:counterexamples}} When attempting to prove the equivalence of non-equivalent functions, the Dafny verifier creates counter-examples, however, these examples are not always as simple as possible, nor are they always correct.
\paragraph{\nameref{sec:equivalence-lemmas}} When the functions being compared both use helper functions, the Dafny verifier requires the user to create separate equivalence lemmas for the helper functions, and call these lemmas within the lemma for the original functions, under the correct conditions and with the correct arguments.
\paragraph{\nameref{sec:auxiliary-lemmas}} Sometimes the Dafny verifier can only prove equivalence by using an auxiliary lemma. These lemmas are often difficult for the verifier to generate. In addition, they must also be called with the correct conditions and with the correct arguments.
\paragraph{\nameref{sec:induction}} The Dafny verifier often proves lemmas using induction, however, the verifier is sometimes unable to infer the induction scheme, requiring the user to explicitly describe it.
\paragraph{\nameref{sec:termination}} The verifier requires a variant to prove each lemma (since they are proved through induction), however, it is often unable to infer one by itself, even when the functions being compared themselves use an appropriate variant. In addition, any termination lemmas or assertions must also be explicitly copied into the equivalence lemma. 
\paragraph{\nameref{sec:imperative-equivalence}} Imperative methods cannot be proven equivalent using lemmas since lemmas must be pure while methods can have side-effects. Therefore, equivalence must instead be proven through postconditions and invariants, which are often complicated. I also explore product programs\parencite{lahiriDifferentialAssertionChecking2013} which can make proving imperative program equivalence easier. 
\paragraph{\nameref{sec:higher-order}} The Dafny verifier sometimes cannot prove the equivalence of higher-order functions despite being able to prove that the outputted functions give the same output for the same inputs.

\subsection{Necessary Datastructures}\label{sec:list-structure}

I will require the following definition of a list data structure:
\begin{dafny}
datatype List<T> = Nil | Cons(head: T, tail: List<T>)
\end{dafny}

\subsection{Incorrect Counterexamples}\label{sec:counterexamples} 
In this example, I will provide two functions that attempt to determine whether a list of integers is sorted in non-decreasing order. The first function is as follows, involving the main function \dafnyinline{isSortedR} and a helper function \dafnyinline{loop}:

\begin{dafny}
function loop(p: int, l: List<int>): bool
  decreases l
{
  match l
  case Nil => true
  case Cons(x, xs) => p <= x && loop(x, xs)
}

function isSortedR(l: List<int>): bool
{
  match l
  case Nil => true
  case Cons(x, xs) => loop(x, xs)
}
\end{dafny}
%
The second function is as follows, involving the main function \dafnyinline{isSortedA} and helper functions \dafnyinline{iter} and \dafnyinline{leq}:

\begin{dafny}[highlightlines=3]
function leq(cur: int, next: int): bool
{
  cur < next
}

function iter(l: List<int>): bool
{
  match l
  case Nil => true
  case Cons(x, Nil) => true
  case Cons(x, Cons(y, ys)) => leq(x, y) && iter(Cons(y, ys))
}

function isSortedA(l: List<int>): bool
{
  match l
  case Nil => true
  case Cons(_, Nil) => true
  case Cons(x, Cons(y, ys)) => x <= y && iter(Cons(y, ys))
}
\end{dafny}
%
These functions are not equivalent, as \dafnyinline{isSortedA} uses a strictly less-than comparison in the \dafnyinline{leq} function, when it should use a less-than-or-equal-to comparison (as highlighted). Therefore, Dafny is unable to prove the following equivalence lemma:
\begin{dafny}
lemma isSortedEquivalence(l: List<int>)
  ensures isSortedA(l) == isSortedR(l)
{}
\end{dafny}
%

However, it incorrectly provides \dafnyinline{Cons(-38, Cons(7681, Nil))} as a counterexample. As found by \textcite{putrueleMaskDToolMeasuring2022}, counterexamples may sometimes be incorrect due to the Z3 solver being incomplete. I extended the above proof to include and use a helper lemma, as shown below:
\begin{dafny}
lemma isSortedEquivalenceHelper(x: int, xs: List<int>)
  decreases xs
  ensures iter(Cons(x, xs)) == loop(x, xs)
{}

lemma isSortedEquivalence(l: List<int>)
  ensures isSortedA(l) == isSortedR(l)
{
  match l
  case Nil => {}
  case Cons(x, Nil) => {}
  case Cons(x, Cons(y, ys)) => isSortedEquivalenceHelper(y, ys);
}
\end{dafny}
%

Now, Dafny is able to provide a correct counterexample of \dafnyinline{x = 8855} and \dafnyinline{xs = Cons(8855, Nil)} for the helper lemma. However, though this is the simplest counterexample in terms of list length, it is not the simplest example in terms of the integers used, as \dafnyinline{x = 0} and \dafnyinline{xs = Cons(0, Nil)} would be sufficient. \textcite{putrueleMaskDToolMeasuring2022} also state that generated counterexamples can sometimes be difficult to read and understand since there are multiple translations steps between the Dafny source code and the verification conditions sent to the Z3 SMT solver.

\subsection{Equivalence Lemmas for Helper functions}\label{sec:equivalence-lemmas}

For this example, I will provide two solutions to the problem of reducing a list down its unique elements. Both solutions each require two helper functions, where each of the three pairs of functions across the two solutions are equivalent. The first pair of functions are \dafnyinline{isin} and \dafnyinline{find}. These functions determine whether a given element is in a list:
\begin{dafny}
function find(lst: List<int>, n: int): bool
{
  match lst
  case Nil => false
  case Cons(hd, tl) => n == hd || find(tl, n)
}

function isin(a: int, lst: List<int>): bool
{
  match lst
  case Nil => false
  case Cons(hd, tl) => a == hd || isin(a, tl)
}
\end{dafny}
%
Dafny requires that these helper functions are explicitly proven equivalent to be able to prove that the main functions are equivalent. Therefore, the user must write the following equivalence lemma:
\begin{dafny}
lemma findEquivalence(l: List<int>, n: int)
  ensures find(l, n) == isin(n, l)
{}
\end{dafny}
%
\textcite{milovancevicProvingDisprovingEquivalence2023} were able to automatically generate these helper lemmas by preprocessing the two solutions to find helper functions with compatible signatures: where the arguments of one function can be permuted so that their types match the types of the arguments of another function. Once candidate pairs of functions are found, equivalence lemmas such as the one above can be automatically generated and proven. If multiple functions share the same signature, test cases are used to narrow down the search space. These can be defined by the user or generated from counterexamples found when disproving equivalence of other incorrect candidate submissions.

The second pair of functions are \dafnyinline{unique} and \dafnyinline{distinct}. These functions take two lists as input, and compute the unique elements of their union:

\begin{dafny}
function unique(l: List<int>, r: List<int>): List<int>
{
  match l
  case Nil => r
  case Cons(hd, tl) =>
    if !find(r, hd) then unique(tl, append(r, Cons(hd, Nil)))
    else unique(tl, r)
}

function distinct(a: List<int>, b: List<int>): List<int>
  decreases b
{
  match b
  case Nil => a
  case Cons(hd, tl) =>
    if isin(hd, a) then distinct(a, tl)
    else distinct(append(a, Cons(hd, Nil)), tl)
}
\end{dafny}
%

To prove their equivalence, the user must write the following equivalence lemma:
\begin{dafny}[highlightlines=6]
lemma uniqEquivalenceHelper(l: List<int>, r: List<int>)
  ensures unique(l, r) == distinct(r, l)
{
  match l
  case Nil => {}
  case Cons(hd, tl) => findEquivalence(r, hd);
}
\end{dafny}
%

Therefore, since the proof of the equivalence of \dafnyinline{unique} and \dafnyinline{distinct} relies on the equivalence of \dafnyinline{find} and \dafnyinline{isin}, the user must explicitly call the equivalence lemma for the helper functions. This lemma must be called with the correct arguments and under the correct conditions, within the main equivalence lemma (the corresponding line is highlighted above).

In addition, this lemma cannot be so easily generated using the method described above, as the arguments of \dafnyinline{unique} and \dafnyinline{distinct} have the same types, but are used in different ways. Therefore, to successfully generate this lemma, the functions themselves must be processed to identify how each argument is used.

Finally, the third pair of functions \dafnyinline{uniqR} and \dafnyinline{uniqA} to find the unique elements of a list are as follows:

\begin{dafny}
function uniqR(lst: List<int>): List<int>
{
  unique(lst, Nil)
}

function uniqA(lst: List<int>): List<int>
{
  distinct(Nil, lst)
}
\end{dafny}
%
These functions can be proven equivalent using the following equivalence lemma:
\begin{dafny}
lemma uniqEquivalence(l: List<int>)
  ensures uniqR(l) == uniqA(l)
{
  uniqEquivalenceHelper(l, Nil);
}
\end{dafny}

\subsection{Generating Auxiliary Lemmas}\label{sec:auxiliary-lemmas}

Sometimes, to prove the equivalence of two functions, Dafny requires helper lemmas that will be difficult to generate automatically, since they require an understanding of what the functions being compared do. For example, consider the following two functions \dafnyinline{limitM} and \dafnyinline{limit1}, which attempt to compute the triangular number of a given integer \dafnyinline{n} (the functions return \dafnyinline{n} when n is negative):

\begin{dafny}[highlightlines=9-11]
function limitM(n: int): int {
  if (n <= 1) then n
  else n + limitM(n-1)
}

function limit1(n: int): int {
  if (n <= 1) then n
  else
    var r := limit1(n-1);
    if (r >= 0) then n + r
    else r
}
\end{dafny}
%
The main difference between these two functions is in the \dafnyinline{else} branch of the \dafnyinline{limit1} function (this is highlighted above). Here, the function will either output \dafnyinline{n + r} or \dafnyinline{r}, depending on whether \dafnyinline{r >= 0}. However, to reach this \dafnyinline{else} branch, we know that \dafnyinline{n} must be greater than or equal to 2, so \dafnyinline{n - 1} must be at least 1. Therefore, \dafnyinline{limit1(n-1)} will output a triangular number, which must be non-negative. This means that we should be able to prove that \dafnyinline{r} is always non-negative, so \dafnyinline{n + r} will always be returned. Dafny requires some help to realise this, and to prove equivalence:

\begin{dafny}
lemma equivalenceLimit3_Helper(n: int)
  requires n >= 1
  ensures limit3_2(n) > 0
{}

lemma equivalenceLimit3(n: int)
  ensures (limit3_1(n) == limit3_2(n))
{
  if n >= 2 { equivalenceLimit3_Helper(n); }
}
\end{dafny}
%
Therefore, Dafny is able to prove the equivalence of these two functions, but only after the user provides a helper lemma that would be difficult for Dafny to automatically generate. Here is another, more complicated example. Consider the following two functions \dafnyinline{m1} and \dafnyinline{m2}, which output the fibonnaci number of a given integer \dafnyinline{n}. However, both functions contain an extra boolean argument: 
\begin{dafny}[highlightlines=11-15]
function m1(n: int, flag: bool): int {
  if (n < 1) then 0
  else if (n == 1) then 1
  else m1(n - 1, !flag) + m1(n - 2, !flag)
}

function m2(n: int, mode: bool): int {
  if (n < 1) then 0
  else if (n == 1 || n == 2) then 1
  else
    var results := if (mode) then
                      m2(n-2, !mode) + m2(n-2, !mode) + m2(n-3, !mode) 
                   else
                      m2(n-1, !mode) + m2(n-2, !mode);
    results
}
\end{dafny}
%
The first function does not use the boolean argument at all. The second function uses it in the \dafnyinline{else} branch (this is highlighted above). Here, the second function either computes the standard fibonacci expression \dafnyinline{m2(n-1, !mode) + m2(n-2, !mode)}, or the expression with the \dafnyinline{m2(n-1, !mode)} call unrolled once (\dafnyinline{m2(n-2, !mode) + m2(n-2, !mode) + m2(n-3, !mode)}). Dafny only requires assistance in proving that the unrolled function call in \dafnyinline{m2} is equivalent to the standard fibonacci expression. Therefore, the user must provide the following auxiliary lemma:

\begin{dafny}
lemma m2_equivalence_fib(n: int)
  requires n >= 2
  ensures m2(n, true) == m2(n - 1, false) + m2(n - 2, false)
{}
\end{dafny}
%
Using this, Dafny can now prove the equivalence of \dafnyinline{m1} and \dafnyinline{m2}:
\begin{dafny}
lemma equivalence(n: int, flag: bool)
  ensures m1(n, flag) == m2(n, flag)
{
  if n >= 2 { m2_equivalence_fib(n); }
}
\end{dafny}

\subsection{Explicitly enforcing induction to prove lemmas}\label{sec:induction}

Dafny often proves lemmas through induction. However, sometimes, it requires the user to explicitly state how to perform this induction by calling the lemma the user is trying to prove recursively with `smaller' arguments. For example, consider the two functions \dafnyinline{binSumM} and \dafnyinline{binSum1}. These functions compute the sum of two binary numbers and a carry bit, where the bits are represented as booleans, and the binary numbers are represented as lists of bits, in order of least significant to most significant. The \dafnyinline{binSum1} function computes the sum by listing every possible form of input, while the \dafnyinline{binSumM} function simplifies this by using the carry bit in a more complicated way. The functions are as follows: 

\begin{dafny}
function binSum1(l1: List<bool>, l2: List<bool>, c: bool): List<bool>
  decreases length(l1) + length(l2)
{
  match (l1, l2, c)
    case (Nil, Nil, _) => Nil
    case (Cons(true, t1), Cons(false, t2), false) => Cons(true, binSum1(t1, t2, false))
    case (Cons(true, t1), Cons(false, t2), true) => Cons(false, binSum1(t1, t2, true))
    case (Cons(false, t1), Cons(true, t2), false) => Cons(true, binSum1(t1, t2, false))
    case (Cons(false, t1), Cons(true, t2), true) => Cons(false, binSum1(t1, t2, true))
    case (Cons(false, t1), Cons(false, t2), false) => Cons(false, binSum1(t1, t2, false))
    case (Cons(false, t1), Cons(false, t2), true) => Cons(true, binSum1(t1, t2, false))
    case (Cons(true, t1), Cons(true, t2), false) => Cons(false, binSum1(t1, t2, true))
    case (Cons(true, t1), Cons(true, t2), true) => Cons(true, binSum1(t1, t2, true))
    case (Cons(true, t1), Nil, true) => Cons(false, binSum1(t1, Nil, true))
    case (Cons(true, t1), Nil, false) => Cons(true, binSum1(t1, Nil, false))
    case (Cons(false, t1), Nil, true) => Cons(true, binSum1 (t1, Nil, false))
    case (Cons(false, t1), Nil, false) => Cons(false, binSum1(t1, Nil, false))
    case (Nil, Cons(true, t1), true) => Cons(false, binSum1(t1, Nil, true))
    case (Nil, Cons(true, t1), false) => Cons(true, binSum1(t1, Nil, false))
    case (Nil, Cons(false, t1), true) => Cons(true, binSum1(t1, Nil, false))
    case (Nil, Cons(false, t1), false) => Cons(false, binSum1(t1, Nil, false))
}

function binSumM(l1: List<bool>, l2: List<bool>, c: bool): List<bool>
  decreases length(l1) + length(l2)
{
  match (l1, l2)
    case (Nil, Nil) => Nil
    case (Cons(true, t1), Cons(false, t2)) => Cons(!c, binSumM(t1, t2, c))
    case (Cons(false, t1), Cons(true, t2)) => Cons(!c, binSumM(t1, t2, c))
    case (Cons(false, t1), Cons(false, t2)) => Cons(c, binSumM(t1, t2, false))
    case (Cons(true, t1), Cons(true, t2)) => Cons(c, binSumM(t1, t2, true))
    case (Cons(true, t1), Nil) => Cons(!c, binSumM(t1, Nil, c))
    case (Cons(false, t1), Nil) => Cons(c, binSumM(t1, Nil, false))
    case (Nil, Cons(true, t2)) => Cons(!c, binSumM(t2, Nil, c))

}

%

lemma equivalenceBinSum(l1: List<bool>, l2: List<bool>, c: bool)

{

    case (Cons(_, t1), Cons(_, t2)) => equivalenceBinSum(t1, t2, c);

\subsection{Providing Variants to prove termination}\label{sec:termination}

Here, I will use the same example I used in \Cref{sec:dafny}. I have copied the equivalence lemma below:
\begin{dafny}[highlightlines=3]
lemma maxEquivalence(l: seq<int>)
  ensures maxC(l) == maxR(l)
  decreases |l|
{}
\end{dafny}
%
Dafny requires a variant to prove termination, as it proves the equivalence lemma through induction. However, in this case, it is unable to infer this variant by itself so the user must provide it instead (this is highlighted above). This problem can be solved easily in some cases, including this one, by copying the variant from one of the functions being compared.

This solution is especially apparent if both functions have the same variant. Here I provide two implementations of a function to subtract one integer from another. The two functions are as follows (the variants are highlighted):
\begin{dafny}[highlightlines={2,10}]
function sub(x: int, y: int): int
  decreases(if (x <= 0) then -x else x) {
  if (x == 0) then -y
  else if (x > 0) then sub(x - 1, y - 1)
  else sub(x + 1, y + 1)
}

// Computes y - x instead of x - y
function mySub(x: int, y: int): int
  decreases(if (y <= 0) then -y else y) {
  if (y == 0) then -x
  else if (y > 0) then mySub(x - 1, y - 1)
  else mySub(x + 1, y + 1)
}
\end{dafny}
%
The variants of these two functions are equivalent when the arguments are matched correctly. Therefore, Dafny is able to prove their equivalence as follows, but only if the user explicitly provides a variant with the same structure as those from the two functions, with the correct arguments:

\begin{dafny}[highlightlines=2]
lemma equivalenceSub(x: int, y: int)
  decreases(if (x <= 0) then -x else x)
  ensures (sub(x, y) == mySub(y, x))
{}
\end{dafny}
%
In addition, if at least one of the functions requires a lemma or an assertion to prove termination, this must be copied into the equivalence lemma as well. For example, here are two implementations of a function to reduce a list down to its unique elements:
\begin{dafny}[highlightlines={6,16}]
function solution2(lst: List<int>): List<int>
  decreases(length(lst)) {
  match lst {
    case Nil        => Nil
    case Cons(hd, tl) =>
      lemM(hd, tl);
      Cons(hd, solution2(drop2(tl, hd)))
  }
}

function uniq2(lst: List<int>): List<int>
  decreases(length(lst)) {
  match lst {
    case Nil => Nil
    case Cons(hd, tl) =>
      lem2(hd, tl);
      Cons(hd, uniq2(drop(hd, tl)))
  }
}
\end{dafny}
%
The functions \dafnyinline{drop2} and \dafnyinline{drop} are helper functions that remove all occurrences of an integer from a list of integers. The definitions of these functions are unnecessary for this example, so I will omit them. All that is required is that they are equivalent, when the arguments are matched correctly:
\begin{dafny}
lemma equivalenceDrop(a: int, lst: List<int>)
  ensures (drop(a, lst) == drop2(lst, a))
{}
\end{dafny}
%
To prove termination, Dafny requires the lists inputted into the recursive calls to \dafnyinline{solution2} and \dafnyinline{uniq2} to be `smaller' than the lists provided in the original calls. Therefore, the outputs of \dafnyinline{drop2} and \dafnyinline{drop} must be `smaller' than the original lists. Dafny cannot infer this by itself, therefore, the user must explicitly provide lemmas. \dafnyinline{solution2} and \dafnyinline{uniq2} use the lemmas \dafnyinline{lemM} and \dafnyinline{lem2} respectively for this purpose (their call sites are highlighted above). These lemmas are equivalent, so I will only provide \dafnyinline{lem2}. For this example, it is sufficient to prove one list is `smaller' than another by using their lengths:
\begin{dafny}
lemma lem2(a: int, lst: List<int>)
  ensures length(drop(a, lst)) <= length(lst)
{}
\end{dafny}
%
Using \dafnyinline{equivalenceDrop}, Dafny is able to prove the equivalence of \dafnyinline{solution2} and \dafnyinline{uniq2}, but only if the user explicitly calls \dafnyinline{lem2}:
\begin{dafny}[highlightlines=8]
lemma equivalence_solution2_uniq2(lst: List<int>)
  ensures (solution2(lst) == uniq2(lst))
  decreases(length(lst))
{
  match lst
    case Nil => {}
    case Cons(hd, tl) =>
      lem2(hd, tl);
      equivalenceDrop(hd, tl);
}
\end{dafny}
%

\subsection{Equivalence of Imperative Methods}\label{sec:imperative-equivalence}

Recursive functions can be converted into their iterative versions. For example, here is a recursive implementation of a function \dafnyinline{isSortedB} to determine whether a sequence of integers is sorted in non-decreasing order:
\begin{dafny}
function isSortedB(l: seq<int>): bool
  decreases |l|
{
  if |l| == 0 then true
  else if |l| == 1 then isSortedB([])
  else l[0] <= l[1] && isSortedB(l[1..])
}
\end{dafny}
%
This implementation can be converted into the following imperative method. It is not an exact conversion from the recursive version, to make better use of imperative features. Both the function and the method use sequences, so that I can use Dafny's built-in indexing and slicing features. The method's postcondition states that it will output a boolean equivalent to whether each element in the sequence is less than or equal to the next element. If this can be proven, then the sequence must be sorted in non-decreasing order. The variable \dafnyinline{index} together with the invariant in the \dafnyinline{while} loop are used to keep track of which sequence elements have been checked so far.
\begin{dafny}
method isSortedBI(l: seq<int>) returns (res: bool)
  ensures res <==> (forall i :: 0 <= i < |l| - 1 ==> l[i] <= l[i+1])
{
  var index := 0;

  while index < |l| - 1
    invariant forall i :: 0 <= i < index ==> (i < |l| - 1 ==> l[i] <= l[i+1])
  {
    if l[index] > l[index + 1] {
        return false;
    }
    index := index + 1;
  }

  return true;
}
\end{dafny}
%
Proving the equivalence of imperative methods cannot be achieved directly through lemmas in Dafny; only functions can be called within lemmas as, by definition, Dafny functions are pure while Dafny methods are allowed to have side effects. Therefore, to prove equivalence, we must prove postconditions for both methods, and then state that these postconditions are equivalent. In turn, as in the above example, the user will often need to provide loop invariants and variants to help Dafny prove these postconditions.

These specifications can be very difficult to write correctly. Additionally, just proving that the methods' postconditions are equivalent is not sufficient to prove the equivalence of the methods themselves, as the postconditions may not fully capture the behaviour of the methods. 

\subsubsection{Proving Equivalence of Imperative Methods using Product Programs}

As described by \textcite{lahiriDifferentialAssertionChecking2013}, one solution to these difficulties is to generate product programs. A product program is a method that contains the bodies of the two methods being compared, in such a way that relationships between the two can be verified.

For example, we can use this process to prove the equivalence of the imperative versions of \dafnyinline{isSortedR} and \dafnyinline{isSortedB} (the function version of \dafnyinline{isSortedR} can be found in \Cref{sec:counterexamples}). The imperative version of \dafnyinline{isSortedR} (called \dafnyinline{isSortedRI}) is as follows, requiring a helper function \dafnyinline{loopI}. As above, the methods are not an exact conversion from their recursive counterparts. Additionally, the \dafnyinline{isSortedR} function operates on Lists, so I have converted it to use sequences instead. 

The helper method \dafnyinline{loopI} returns a boolean representing whether an integer \dafnyinline{p} prepended to a list of integers \dafnyinline{l} is a list sorted in non-decreasing order. The function's postcondition verifies this by finding whether the list \dafnyinline{l} is sorted, and whether \dafnyinline{p} is less than or equal to the first value in \dafnyinline{l} (if \dafnyinline{l} is non-empty). \dafnyinline{loopI} implements this by maintaining a `rolling' comparison of adjacent list elements. It starts by comparing \dafnyinline{p} and the first element of \dafnyinline{l}, and continues by comparing adjacent elements of \dafnyinline{l}. The variable \dafnyinline{next} represents how far the loop has progressed through the list \dafnyinline{l}. The \dafnyinline{isSortedRI} method calls the helper method \dafnyinline{loopI} for non-empty lists and returns \dafnyinline{true} for empty lists:

\begin{dafny}
method loopI(p: int, l: seq<int>) returns (res: bool)
  ensures res <==> ((forall i :: 0 <= i < |l| - 1 ==> l[i] <= l[i+1]) && (|l| > 0 ==> p <= l[0]))
{
  var currentP := p;
  var next := 0;

  while next < |l|
    invariant next <= |l|
    invariant currentP == if next == 0 then p else l[next - 1]
    invariant next > 0 ==> p <= l[0]
    invariant forall i :: 0 <= i < next - 1 ==> l[i] <= l[i+1]
  {
    if currentP > l[next] {
        return false;
    }
    currentP := l[next];
    next := next + 1;
  }

  return true;
}

method isSortedRI(l: seq<int>) returns (res: bool)
  ensures res <==> (forall i :: 0 <= i < |l| - 1 ==> l[i] <= l[i+1])
{
  if |l| == 0 {
    return true;
  } else {
    var result := loopI(l[0], l[1..]);
    return result;
  }
}
\end{dafny}
%
These methods can be used to construct a product program as follows, using the definition of \dafnyinline{loopI} given above:
\begin{dafny}
method isSortedBI_RI_Equivalence(lb: seq<int>, lr: seq<int>) returns (rres: bool, bres: bool)
  requires lb == lr
  ensures rres == bres
{
  // Defining output variables
  var rout: bool;
  var bout: bool;

  // Computing isSortedRI
  if |lr| == 0 {
    rout := true;
  } else {
    var result := loopI(lr[0], lr[1..]);
    rout := result;
  }

  // Computing isSortedBI
  var index := 0;

  while index < |lb| - 1
    invariant forall i :: 0 <= i < index ==> (i < |lb| - 1 ==> lb[i] <= lb[i+1])
  {
    if lb[index] > lb[index + 1] {
        return rout, false;
    }

    index := index + 1;
  }

  bout := true;

  // Returning the results
  return rout, bout;
}
\end{dafny}
%

The specification of this product program ensures that, since Dafny is able to verify this method, \dafnyinline{isSortedBI} and \dafnyinline{isSortedRI} must be equivalent. Therefore, this process removes the need for the user to provide postconditions for the individual methods, that capture their behaviour fully. In this case, a postcondition for the \dafnyinline{loopI} helper function is still required, but the body of this method can also be copied into the product program, removing this requirement as well. However, the user must still provide the loop invariants and variants for the individual methods.

\subsubsection{Equivalence of Methods and Functions}

A similar problem to that discussed above is proving the equivalence of a method and a function. In this case, the user does not need to write a postcondition for the method, since the function can be called directly within the specification. The user still needs to provide loop invariants and variants for the method, however, these do not need to be as complicated as those detailed above as they can again be defined in terms of the function. For example, the function \dafnyinline{isSortedB} defined in \Cref{sec:imperative-equivalence} can be proven to be equivalent with the following imperative method:
\begin{dafny}
method isSortedBI(l: seq<int>) returns (res: bool)
  ensures res == isSortedB(l)
{
  var index := 0;

  while index < |l| - 1
    invariant index <= |l|
    invariant isSortedB(l[index..]) == isSortedB(l)
  {
    if l[index] > l[index + 1] {
        return false;
    }
    index := index + 1;
  }

  return true;
}
\end{dafny}

\subsection{Equivalence of Higher-Order Functions}\label{sec:higher-order}

Dafny is able to prove the equivalence of some higher-order functions, but not all. For example, here are two functions \dafnyinline{andThen1} and \dafnyinline{andThen2}, which compute function composition:
\begin{dafny}
function andThen1<A, B, C>(f: A -> B, g: B -> C): A -> C { a => g(f(a)) }
function andThen2<A, B, C>(ff: A -> B, gg: B -> C): A -> C { aa => gg(ff(aa)) }
\end{dafny}
%
Dafny is able to prove their equivalence without any help:
\begin{dafny}
lemma equivalenceAndThen<A, B, C>(f: A -> B, g: B -> C)
  ensures andThen1(f, g) == andThen2(f, g)
{}
\end{dafny}
%
Here are two more such functions \dafnyinline{flip1} and \dafnyinline{flip2}, which each take a binary function as input, and output a function that computes the same output, but with the arguments flipped:
\begin{dafny}
function flip1<A, B, C>(f: (A, B) -> C): (B, A) -> C {
  (b, a) => f(a, b)
}

function flip2<A, B, C>(f: (A, B) -> C): (B, A) -> C {
  (b, a) => var res := f(a, b); res
}
\end{dafny}
%
Dafny is able to prove that the outputted functions give the same output for the same inputs:
\begin{dafny}
lemma equivalenceFlip<A, B, C>(f: (A, B) -> C)
  ensures forall b: B, a: A :: flip1(f)(b, a) == flip2(f)(b, a)
{}
\end{dafny}
%
However, it is unable to prove that the outputted functions themselves are equivalent:
\begin{dafny}
// Dafny cannot prove this lemma
lemma equivalenceFlip<A, B, C>(f: (A, B) -> C)
  ensures flip1(f) == flip2(f)
{}
\end{dafny}
