function repeat1<A>(n: int, f: A -> A): A -> A
  requires (n >= 0)
  decreases(n) {
  a =>

lemma equivalenceRepeat12<A>(n: int, f: A -> A, a: A)

\section{EquiDafny Sub-Expression equivalence assumption}

After creating my evaluation testsuite, I identified an assumption in the function merging algorithm that limits its performance. The algorithm assumes that, when expressions are equivalent and have the same structure, their sub-expressions are also equivalent. This allows the algorithm to split up expressions into their constituent parts and recursively merge them together. However, this assumption does not always hold. 

For example, match expressions can be equivalent even when their scrutinees have different structures. An example that demonstrates this is in \Cref{sec:induction}. In this example, the scrutinees are \dafnyinline{(l1, l2)} and \dafnyinline{(l1, l2, c)}. They have different structures since they are tuples with different lengths. EquiDafny cannot merge the patterns in these match expressions, since they are also tuples with different lengths. Thus, EquiDafny cannot prove the equivalence of these functions.

Another example of when this assumption does not always hold is when calling helper functions. Helper functions do not need to be equivalent for the main functions to be equivalent, even when the helper functions are called in the same way. For example, here are the functions \dafnyinline{oddM} and \dafnyinline{odd1}. Each function determines whether a given integer is odd or even by outputting 1 for odd numbers and 0 for even numbers. They each use the helper functions \dafnyinline{libM} and \dafnyinline{lib1} respectively (the calls to these helper functions are highlighted):
\begin{dafny}[highlightlines={3,15}]
function oddM(x: int): int 
{
  if libM(x) == 0 then 1 
  else 0
}

function libM(x: int): int
{
  (x + 1) % 2
}

function odd1(x: int): int 
  requires x > 0
{
  if lib1(x) == 0 then 1 
  else 0
}

function lib1(x: int): int
  requires x > 0
{
  if x % 2 == 0 then 1 + lib1(x / 2)
  else 0
}
\end{dafny}
%
EquiDafny assumes that, since the functions \dafnyinline{oddM} and \dafnyinline{odd1} have the same structure and call the helper functions \dafnyinline{libM} and \dafnyinline{lib1} in the same way, the helper functions themselves must be equivalent. However, in this case, this is not true. The \dafnyinline{libM} function outputs whether \dafnyinline{x + 1} is even or not. Therefore, the function outputs 0 when given an odd number and outputs 1 when given an even number. Meanwhile, the \dafnyinline{lib1} function outputs 0 when given an odd number and outputs a number greater than 0 when given an even number. Therefore, the helper functions are not equivalent. However, the main functions \dafnyinline{oddM} and \dafnyinline{odd1} only check whether the helper functions output 0. The helper functions are equivalent in this respect: both output 0 when they are given an odd number and neither output 0 when they are given an even number. Therefore, the main functions \dafnyinline{oddM} and \dafnyinline{odd1} are equivalent, despite the helper functions not being equivalent. EquiDafny does not realise this and so is unable to prove equivalence. Equivalence can be proven with the following lemmas:
\begin{dafny}
lemma lib1Helper(x: int)
  requires x > 0
  ensures x % 2 == 0 ==> lib1(x) > 0
{}

lemma equivalence(x: int)
  requires x > 0
  ensures oddM(x) == odd1(x)
{
  lib1Helper(x);
}
\end{dafny}

\section{EquiDafny Functionality Limitations}\label{sec:eval-limitations}

There are several tests which EquiDafny fails to prove but Stainless succeeds. EquiDafny could verify these tests if additional functionality were implemented. I have identified three types of additional functionality and described them below. 

\subsection{Flattening match expressions}\label{sec:match-flattening}

Nested match expressions should be flattened into a single match expression so that they can be merged effectively. Nested if expressions should also be flattened, however, since all if expressions are converted into match expressions (as described in \Cref{sec:benefits-drawbacks}), a separate process for if expressions is not necessary. For example, here are two functions called \dafnyinline{maxM} and \dafnyinline{max3} that find the maximum of a list. Similar to the example in \Cref{sec:dafny}, these functions process the list in opposite directions. However, these functions use a user-defined \dafnyinline{List} type instead of Dafny's inbuilt \dafnyinline{seq} type:
\begin{dafny}[highlightlines={11,18}]
function maxM(lst: List<int>): int
  decreases(lst) {
  match lst {
    case Nil             => -1
    case Cons(hd, Nil)   => hd
    case Cons(hd, tl)    => if (hd > maxM(tl)) then hd else maxM(tl)
  }
}

function max3(l: List<int>): int
  decreases(length(l)) {
  match l {
    case Nil => -1
    case Cons(hd, tl) =>
      match tl {
        case Nil => hd
        case Cons(hd1, tl1) =>
          assert length(Cons(hd, tl1)) < length(l);
          if (hd > hd1) then max3(Cons(hd, tl1)) else max3(Cons(hd1, tl1))
      }
  }
}
\end{dafny}
%
The \dafnyinline{max3} function uses the \dafnyinline{length} function in its variant and requires an assertion to prove termination (as highlighted). These will be addressed in \Cref{sec:candidate-copying}. There is a nested match expression in the \dafnyinline{Cons(hd, tl)} case in the body of the \dafnyinline{max3} function. This must be flattened into the following single match expression:
\begin{dafny}
match l {
  case Nil => -1
  case Cons(hd, Nil) => hd
  case Cons(hd, Cons(hd1, tl1)) => 
    assert length(Cons(hd, tl1)) < length(l);
    if (hd > hd1) then max3(Cons(hd, tl1)) else max3(Cons(hd1, tl1))
}
\end{dafny}
%
Now, the bodies of the two functions can be correctly merged together. I will provide the lemma that proves their equivalence in \Cref{sec:candidate-copying}. 

\subsection{Copying from candidate functions}\label{sec:candidate-copying}

For the majority of the tests in the evaluation testsuite, it is sufficient to generate equivalence lemmas by copying structures from the model function alone. However, in some cases, structures must be copied from the candidate function as well, including termination lemma calls, preconditions and assertions. I will demonstrate this using the example described in \Cref{sec:match-flattening}. In this example, the Dafny verifier struggles to prove termination in the candidate function \dafnyinline{max3}. The user must provide the \dafnyinline{length} function and use it within the function's variant and within an assertion in the last match case. The \dafnyinline{length} function is provided below:
\begin{dafny}
function length<T>(l: List<T>): nat
  decreases(l) {
  match l {
    case Nil        => 0
    case Cons(_, t) => 1 + length(t)
  }
}
\end{dafny}
%
Because of this, the corresponding equivalence lemma must use the termination structures from the \dafnyinline{max3} function rather than the \dafnyinline{maxM} function, as the Dafny verifier is unable to prove termination otherwise. Thus, the variant and assertion from the candidate function \dafnyinline{max3} must be copied into the equivalence lemma. However, these structures refer to variables defined within the candidate function. For example, both the variant and the assertion refer to the variable \dafnyinline{l}. The corresponding variable in the model function is called \dafnyinline{lst}. Therefore, since variables are all defined using structures from the model function, the \dafnyinline{l} variable will be undefined. One solution to this is to replace all candidate variables with their corresponding model variables. As described in \Cref{sec:parameter-mappings}, a mapping between corresponding parameters is maintained during the merging process, thus, this could be used to replace the variables. 

Further problems with variables occur when merging match patterns (as described in \Cref{sec:merging-match-expressions}) since the patterns themselves can define variables. When merging the bodies of the \dafnyinline{maxM} and \dafnyinline{max3} functions, the pattern \dafnyinline{Cons(hd, tl)} will be merged with the pattern \dafnyinline{Cons(hd, Cons(hd1, tl1))} (after match expression flattening, as described in \Cref{sec:match-flattening}). This is necessary for the assertion to be found and copied into the correct place in the equivalence lemma. However, the candidate pattern defines the variable \dafnyinline{tl1}, which is used in the assertion. Thus, if the pattern from the model function (\dafnyinline{Cons(hd, tl)}) is used, the variable \dafnyinline{tl1} will be undefined. Therefore, the pattern from the candidate function (\dafnyinline{Cons(hd, Cons(hd1, tl1))}) must be used instead. This results in the following equivalence lemma:
\begin{dafny}
lemma equivalenceMax3(lst: List<int>)
  ensures (max3(lst) == maxM(lst))
  decreases(length(lst))
{
  match lst {
    case Nil => {}
    case Cons(hd, Nil) => {}
    case Cons(hd, Cons(hd1, tl1)) => assert length(Cons(hd, tl1)) < length(lst);
  }
}
\end{dafny}
%
\subsection{Variable Inlining}

Dafny functions can be defined using variables declarations. The bodies of these variables must sometimes be merged together. For example, here are two functions \dafnyinline{mapM} and \dafnyinline{map1}. Each function takes a list of tuples each containing two integers. Each function outputs a list containing the sums of the integers in each tuple. The functions \dafnyinline{mapM} and \dafnyinline{map1} use helper functions \dafnyinline{sumM} and \dafnyinline{sum1} respectively:
\begin{dafny}[highlightlines={5,22}]
function mapM(l: List<(int, int)>): List<int> {
  match l {
    case Nil => Nil
    case Cons((h1, h2), t) => 
      var hM := sumM(h1, h2);
      Cons(hM, mapM(t))
  }
}

function sumM(x: int, y: int): int
  decreases if x > 0 then x else -x
{
  if x == 0 then y
  else if x < 0 then sumM(x + 1, y - 1)
  else sumM(x - 1, y + 1)
}

function map1(l: List<(int, int)>): List<int> {
  match l {
    case Nil => Nil
    case Cons((h1, h2), t) => 
      var h1 := sum1(h1, h2);
      Cons(h1, map1(t))
  }
}

function sum1(x: int, y: int): int {
  x + y
}
\end{dafny}
%
To create the equivalence lemma between functions \dafnyinline{mapM} and \dafnyinline{map1}, EquiDafny must create an equivalence lemma between the helper functions \dafnyinline{sumM} and \dafnyinline{sum1}. EquiDafny will only realise this if it tries to merge the function calls \dafnyinline{sumM(h1, h2)} and \dafnyinline{sum1(h1, h2)}. Therefore, the bodies of the declarations of the variables \dafnyinline{hM} and \dafnyinline{h1} must be merged together (the variable declarations are highlighted). However, variable declarations cannot be arbitrarily merged together since they can be used for any purpose. EquiDafny should only merge expressions if they are used for the same purpose. Therefore, one solution to this is to substitute the bodies of variable declarations into the places where they are used. This will make it clear to EquiDafny what each variable was used for, making sure it only merges expressions with the same purpose. In this example, the functions \dafnyinline{mapM} and \dafnyinline{map1} will become the following:
\begin{dafny}
function mapM(l: List<(int, int)>): List<int> {
  match l {
    case Nil => Nil
    case Cons((h1, h2), t) => Cons(sumM(h1, h2), mapM(t))
  }
}

function map1(l: List<(int, int)>): List<int> {
  match l {
    case Nil => Nil
    case Cons((h1, h2), t) => Cons(sum1(h1, h2), map1(t))
  }
}
\end{dafny}
%
After this transformation, EquiDafny would be able to generate the following equivalence lemmas:
\begin{dafny}
lemma sumEquivalence(x: int, y: int)
  ensures sumM(x, y) == sum1(x, y)
  decreases if x > 0 then x else -x
{}

lemma equivalence(l: List<(int, int)>)
  ensures mapM(l) == map1(l)
{
  match l {
    case Nil => {}
    case Cons((h1, h2), t) => sumEquivalence(h1, h2);
  }
}
\end{dafny}

Dafny verification takes significantly more time on average than any other component. The vast majority of this time is likely spent by the Z3 solver. The flame graphs demonstrate that Parsley accounts for a significant amount of both EquiDafny's CPU and memory usages. The Parsley stack traces are also very deep (this could not easily be demonstrated in the above figures), reaching several hundreds of blocks deep. Specifically, the majority of the Parsley usages occur in `parsley/internal/deepembedding', where Parsley processes the user-defined parser before it is executed. Therefore, this high Parsley CPU and memory usage cannot be easily removed. To maximise EquiDafny's performance, I would need to switch from Parsley to a parser generator (such as ANTLR~\parencite{DefinitiveANTLR4}) as they are written to maximise performance, however, such a change has other drawbacks that should be considered, including an extra compilation step and the generated code often being difficult to step through and debug.
