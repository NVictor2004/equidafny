\chapter{Design}\label{chp:design}

\paragraph{Terminology} I will use the terms `model function' and `candidate function' to describe the functions that the tool is attempting to create an equivalence proof for. These terms were inspired by \textcite{milovancevicProvingDisprovingEquivalence2023}, where the `model function' described the correct implementation of a function within a functional programming assignment, while the `candidate function' described a student's attempt at implementing the same function for themselves. The tool this project describes can be used for tasks far beyond functional programming assignments, but I will use these terms as a convenient method of referring to the functions being processed. 

\section{Function Merging}\label{sec:function-merging}

This tool will use an approach that I have called `Function Merging'. This is where the bodies of the model and candidate functions are processed simultaneously, creating a set of mappings between the parameters of the two functions and a list of statements. These two outputs are used to create the equivalence lemma for that pair of functions. 

\subsection{Worked Example}\label{sec:worked-example}

To demonstrate how this process works, I will use the two functions \dafnyinline{unique} and \dafnyinline{distinct} (this example was also used in \Cref{sec:equivalence-lemmas}). These functions each take two lists as input, and compute the unique elements of their union:

\begin{dafny}
function unique(l: List<int>, r: List<int>): List<int>
{
  match l
  case Nil => r
  case Cons(hd, tl) =>
    if !find(r, hd) then unique(tl, append(r, Cons(hd, Nil)))
    else unique(tl, r)
}

function distinct(a: List<int>, b: List<int>): List<int>
  decreases b
{
  match b
  case Nil => a
  case Cons(hd, tl) =>
    if isin(hd, a) then distinct(a, tl)
    else distinct(append(a, Cons(hd, Nil)), tl)
}
\end{dafny}
%

I will refer to the \dafnyinline{unique} function as the model function, and the \dafnyinline{distinct} function as the candidate function.

As described in \Cref{sec:equivalence-lemmas}, there are two problems we must address to create an equivalence lemma for these functions. First, the parameters of the model function must each be matched to one of the parameters of the candidate function that serves the same purpose. In simpler examples, the types of the parameters can be used to construct these mappings, however, since in this example each function has multiple parameters with the same type, we must process the bodies of the functions to construct these mappings.

Second, the model and candidate functions each refer to the functions \dafnyinline{find} and \dafnyinline{isin} respectively. Therefore, these helper functions must also be merged recursively, an equivalence lemma must be created for them, and this lemma must be called in the main equivalence lemma for the \dafnyinline{unique} and \dafnyinline{distinct} functions, with the correct arguments and under the correct conditions. 

Therefore, the Function Merging process will work as follows. Since the bodies of the two functions have the same structure (they are both match expressions), these structures can be split up into smaller components, which can then each be merged one at a time. First, the expressions \dafnyinline{l} and \dafnyinline{b} are merged. This creates the parameter mapping \dafnyinline{b -> l} (parameter mappings are always from candidate parameters to model parameters). Next, we merge the \dafnyinline{case} expressions. In this case, the patterns in the two match expressions are the same, thus we can merge the \dafnyinline{case} expressions corresponding to the same pattern together. Merging the expressions corresponding to the \dafnyinline{Nil} pattern creates the parameter mapping \dafnyinline{a -> r}. Thus, we have now created mappings between all function parameters. Merging the expressions corresponding to the \dafnyinline{Cons} pattern requires merging the functions \dafnyinline{find} and \dafnyinline{isin}. This is achieved using the same process recursively. Let us assume that this process resulting in the following equivalence lemma:

\begin{dafny}
lemma findEquivalence(l: List<int>, n: int)
  ensures find(l, n) == isin(n, l)
{}
\end{dafny}
%
Equivalence lemmas are generated in such a way that they must be called by copying the arguments used in the model function. Therefore, this lemma must be called with \dafnyinline{findEquivalence(r, hd)}.

Finally, the main equivalence lemma must be created. Using the parameter mappings \dafnyinline{b -> l} and \dafnyinline{a -> r}, we can determine that the order of the arguments passed into the model function should be swapped when they are passed into the candidate function. This results in the lemma's postcondition being \dafnyinline{unique(l, r) == distinct(r, l)}. To create the body of the lemma, we will copy the match expression in the model function, replacing the \dafnyinline{case} expressions with the statements created by merging them with the corresponding expressions in the candidate function. This results in the following equivalence lemma:

\begin{dafny}
lemma uniqueEquivalence(l: List<int>, r: List<int>)
  ensures unique(l, r) == distinct(r, l)
{
  match l
  case Nil => {}
  case Cons(hd, tl) => findEquivalence(r, hd);
}
\end{dafny}

\subsection{Benefits and Drawbacks}

As described in \Cref{sec:equivalence-lemmas}, to prove the equivalence of two functions that both use helper functions, the tool must generate equivalence lemmas between the helper functions and call these lemmas within the main equivalence lemma under the correct conditions and with the correct arguments. As demonstrated in \Cref{sec:worked-example}, the Function Merging process is capable of this. 

However, one major drawback with this approach is that it requires the bodies of the functions to have the same structure. For example, here are two functions \dafnyinline{lengthM} and \dafnyinline{length1}, which each calculate the length of a list:
\begin{dafny}
function lengthM<T>(l: List<T>): int {
    match l {
        case Nil => 0
        case Cons(_, t) => 1 + lengthM(t)
    }
}

function length1<T>(l: List<T>): int {
    if l == Nil then 0 else 1 + length1(l.tail)
}
\end{dafny}
%

The bodies of these two functions have different structures, therefore, the Function Merging process will fail. The tool uses two methods to attempt to mitigate this issue.

First, the tool will still attempt to generate an equivalence lemma even when the Merging process fails. In this case, such an equivalence lemma will have an empty body, since the Merging process failed immediately. Its parameter mappings can be generated without using the function bodies since there is only a single parameter in each function. Thus, in this case, the following lemma can be generated:

\begin{dafny}
lemma lengthEquivalence<T>(l: List<T>)
    ensures lengthM(l) == length1(l)
{}
\end{dafny}
%
In this case, this lemma is sufficient for the Dafny verifier to prove equivalence. Therefore, EquiDafny can still prove equivalence in some cases despite the Merging process failing. However, this method is not sufficient for every case. For example, here are two equivalent functions to calculate the length of a list in a tail-recursive manner:
\begin{dafny}
function lengthTailM<T>(acc: int, l: List<T>): int
    decreases l
{
    match l {
        case Nil => acc
        case Cons(_, t) => lengthTailM(acc + 1, t)
    }
}

function lengthTail1<T>(l: List<T>, acc: int): int
    decreases l
{
    match l {
        case Nil => acc
        case Cons(_, t) => lengthTail1(t, acc + 1)
    }
}
\end{dafny}
%

I can now reimplement functions \dafnyinline{lengthM} and \dafnyinline{length1} to use these tail-recursive helper functions:
\begin{dafny}
function lengthM<T>(l: List<T>): int {
    match l {
        case Nil => 0
        case Cons(_, t) => lengthTailM(1, t)
    }
}

function length1<T>(l: List<T>): int {
    if l == Nil then 0 else lengthTail1(l.tail, 1)
}
\end{dafny}
%
% TODO: Wrap A && B in inline code
In this case, EquiDafny will still generate the empty equivalence lemma shown above, however, this is no longer sufficient to prove equivalence. The second method of mitigating the problem of the Merging process failing is by translating both function bodies into the same equivalent structure. For example, for arbitrary Boolean formulae \dafnyinline{A} and \dafnyinline{B}, the expressions A \&\& B and \dafnyinline{if A then B else false} are equivalent. Thus, one type of expression can be translated into the other so that they have the same structure. 

This example requires two translations on the \dafnyinline{length1} function's body before it has the same structure as the \dafnyinline{lengthM} function's body. First, the if expression that forms the \dafnyinline{length1} function's body can be translated into a match expression. In general, for arbitrary expressions \dafnyinline{A}, \dafnyinline{B} and \dafnyinline{C}, the expression \dafnyinline{if A then B else C} is equivalent to the following match expression:
\begin{dafny}
match A {
    case true => B
    case false => C
}
\end{dafny}
%
Therefore, the body of the \dafnyinline{length1} function will be translated into the following:
\begin{dafny}
match l == Nil {
    case true => 0
    case false => lengthTail1(l.tail, 1)
}
\end{dafny}
%
Second, this match expression can be simplified by splitting up the equality operation between \dafnyinline{l} and \dafnyinline{Nil} and moving the \dafnyinline{Nil} literal into the match case patterns. This results in the following match expression:
\begin{dafny}
match l {
    case Nil => 0
    case _ => lengthTail1(l.tail, 1)
}
\end{dafny}
%
This final match expression has the same structure as the body of the \dafnyinline{lengthM} function. This allows Function Merging to proceed, leading EquiDafny to produce the following equivalence lemmas:
\begin{dafny}
lemma lengthTailEquivalence<T>(acc: int, l: List<T>)
    decreases l
    ensures lengthTailM(acc, l) == lengthTail1(l, acc)
{}

lemma lengthEquivalence<T>(l: List<T>)
    ensures lengthM(l) == length1(l)
{
    match l {
        case Nil => 
        case Cons(_, t) => lengthTailEquivalence(1, t);
    }
}
\end{dafny}
%

\section{Technical Audit Challenges}

In \Cref{sec:audit}, I demonstrated that Dafny encounters several types of challenges when attempting to prove program equivalence. In this section, I will describe how our tool attempts to remove most of these challenges. The process of generating and calling equivalence lemmas for helper functions has already been described in \Cref{sec:worked-example} (the challenge this refers to is described in \Cref{sec:equivalence-lemmas}). 

\subsection{\nameref*{sec:induction}}
As described in \Cref{sec:induction}, when the functions being processed both recurse in the same way, the Dafny verifier sometimes requires the user to call the equivalence lemma the user is trying to prove recursively. I could not find a rule to determine whether the verifier would need such a call to be written, therefore, our tool will recursively call the equivalence lemma it is currently proving every time the functions being compared both recurse. This approach leads to some equivalence lemma bodies being larger and more complex than the Dafny verifier requires them to be, however, this technique resolves the induction enforcement challenge.

\subsection{\nameref*{sec:higher-order}}
As described in \Cref{sec:higher-order}, the Dafny verifier is not able to prove the equivalence of all higher-order functions automatically, despite being able to prove that the outputted functions give the same output for the same inputs.

To resolve this challenge, when generating the postconditions for lemmas, our tool will pass in the same arguments to both lambda functions so that the Dafny verifier will prove equivalence on the bodies of the lambda functions rather than the lambda functions themselves. For example, here are two functions that implement uncurrying:

\begin{dafny}
function uncurry1<A, B, C>(f: A -> B -> C): (A, B) -> C {
    (a, b) => f(a)(b)
}

function uncurry2<A, B, C>(f: A -> B -> C): (A, B) -> C {
    (a, b) => var res := f(a)(b); res
}
\end{dafny}
%
When generating the corresponding equivalence lemma, instead of attempting to prove equivalence on the lambda functions themselves (\dafnyinline{uncurry1(f)} and \dafnyinline{uncurry2(f)}), the tool will pass the same arguments to both lambda functions so that the function bodies can be directly compared:

\begin{dafny}
lemma uncurry1_uncurry2_Equivalence<A, B, C>(f: A -> B -> C, a: A, b: B)
ensures (uncurry1(f)(a, b) == uncurry2(f)(a, b))
{}
\end{dafny}
%
If the bodies of the outputted lambda functions are themselves lambda functions, our tool will repeatedly pass the same arguments to both functions, until it reaches the body of the innermost lambda function. For example, here are two functions that implement currying:

\begin{dafny}
function curry1<A, B, C>(f: (A, B) -> C): A -> B -> C {
    a => b => f(a, b)
}

function curry2<A, B, C>(f: (A, B) -> C): A -> B -> C {
    aa => bb => var res := f(aa, bb); res
}
\end{dafny}
%

Our tool will produce the following equivalence lemma:
\begin{dafny}
lemma curry1_curry2_Equivalence<A, B, C>(f: (A, B) -> C, a: A, b: B)
ensures (curry1(f)(a)(b) == curry2(f)(a)(b))
{}
\end{dafny}
%

\subsection{\nameref*{sec:auxiliary-lemmas}}
As described in \Cref{sec:auxiliary-lemmas}, proving equivalence sometimes requires auxiliary lemmas that would be difficult for our tool or Dafny to automatically generate. Therefore, these lemmas must be written by the user and provided to our tool. As described in \Cref{sec:user-interface}, the user must provide the path to a Dafny file in the JSON configuration file. The user can provide our tool with any necessary auxiliary lemmas by writing them in this Dafny file.

Thus, the lemmas themselves can be provided, however, they must still be called within the generated equivalence lemmas, with the correct arguments and under the correct conditions. These conditions and arguments cannot be easily generated, since this requires an understanding of what each auxiliary lemma proves and how it would be useful when proving an equivalence lemma. Thus, this is a difficult problem that EquiDafny does not currently solve. 

\section{Technical Details}\label{sec:technical-details}

\subsection{Generating Parameter Mappings}

Parameter Mappings are generated in multiple stages. First, if only a single parameter in each function is of a specific type, then these parameters must be mapped together. For example, given the following signatures for the functions \dafnyinline{f} and \dafnyinline{g}:
\begin{dafny}
function f(a: int, b: bool, c: bool): int
function g(x: bool, y: int, z: bool): int
\end{dafny}
%
Parameters \dafnyinline{a} and \dafnyinline{y} can immediately be mapped together, since they are each the only \dafnyinline{int} parameter in their respective functions. However, parameters \dafnyinline{b}, \dafnyinline{c}, \dafnyinline{x} and \dafnyinline{z} cannot be mapped in this way. Mappings can also be generated when the model parameter's type can be transformed into the candidate parameter's type through a type transformation function (see \Cref{sec:type-transformations}). Parameter mappings are stored by mapping candidate function parameters to model function parameters.

After these mappings are generated, the bodies of the functions are merged together to generate further mappings (as described in \Cref{sec:worked-example}). During the Function Merging process, the map of mappings is continuously updated. A reference to it is passed through all merging functions so that the algorithm always has access to the most up-to-date set of mappings. This is necessary when merging Function Calls (see \Cref{sec:merging-calls}). 

After merging the function bodies, if some parameters have still not been mapped, EquiDafny generates mappings between any pair of the remaining parameters with compatible types (either the same type or when the model parameter's type can be transformed into the candidate parameter's type). This ensures that every parameter is mapped. 

\subsection{Mutually Recursive Functions}\label{sec:mutually-recursive}
Mutually recursive functions must be dealt with carefully during the Function Merging process. For example, here are two functions \dafnyinline{isEven} and \dafnyinline{myIsEven} which each output whether a given integer is even or not. They use the helper functions \dafnyinline{isOdd} and \dafnyinline{myIsOdd} respectively to achieve this, where these helper functions each output whether a given integer is odd or not. The implementations of all four functions are as follows:

\begin{dafny}[highlightlines={5,12,19,26}]
function isEven(x: int): bool
  decreases(if (x <= 0) then 0 else x) {
  if (x < 0) then false
  else if (x == 0) then true
  else !isOdd(x - 1)
}

function myIsEven(x: int): bool
  decreases(if (x <= 0) then 0 else x) {
  if (x < 0) then false
  else if (x == 0) then true
  else !myIsOdd(x - 1)
}

function isOdd(x: int): bool
  decreases(if (x <= 0) then 0 else x) {
  if (x <= 0) then false
  else if (x == 1) then true
  else !isEven(x - 1)
}

function myIsOdd(x: int): bool
  decreases(if (x <= 0) then 0 else x) {
  if (x <= 0) then false
  else if (x == 1) then true
  else !myIsEven(x - 1)
}
\end{dafny}

Let the functions \dafnyinline{isEven} and \dafnyinline{myIsEven} be the model and candidate functions respectively. All function calls are highlighted. During the Function Merging process for these two functions, since their bodies have the same structure, this will result in our tool attempting to merge the function calls \dafnyinline{isOdd(x - 1)} and \dafnyinline{myIsOdd(x - 1)}. This requires the functions \dafnyinline{isOdd} and \dafnyinline{myIsOdd} themselves to be merged. However, when processing these two functions in the same way, this will lead to the functions \dafnyinline{isEven} and \dafnyinline{myIsEven} needing to be merged again, leading to an infinite loop. Therefore, a successful Function Merging implementation must account for mutual recursive functions. 

Our tool solves this problem in the following way. During Function Merging, the process has access to the lemmas currently being generated. This is stored in a map from the name of the model function to an optional lemma (represented using the Scala data structure \dafnyinline{Option}). When the Merging process encounters two function calls, this map is consulted to determine how the process should proceed.

There are three possibilities. First, if the model function name is not a key in this map, then the functions themselves should be merged together. In the above example, when processing the functions \dafnyinline{isEven} and \dafnyinline{myIsEven} for the first time and encountering the function calls to \dafnyinline{isOdd} and \dafnyinline{myIsOdd}, \dafnyinline{isOdd} should not be a key in the map, leading to the functions themselves being merged. Second, if the name of the model function is mapped to a lemma (wrapped in a \dafnyinline{Some} object), then the corresponding lemma has already been generated. Thus, this lemma can be called without further merging. This also prevents the generation of the same lemma multiple times.

Finally, if the model function's name is mapped to the \dafnyinline{None} object, this means that the corresponding lemma is currently being generated. In our example, when processing the functions \dafnyinline{isOdd} and \dafnyinline{myIsOdd} and encountering the function calls to \dafnyinline{isEven} and \dafnyinline{myIsEven}, \dafnyinline{isEven} should be mapped to the \dafnyinline{None} object since the process reached this point during the Merging of \dafnyinline{isEven} and \dafnyinline{myIsEven}. Our tool responds to this by creating a call to the corresponding lemma before the lemma is completely generated. This is possible since the names and parameters of lemmas are always generated consistently. Therefore, by using this map and by carefully updating it during Function Merging, our tool can successfully deal with mutually recursive functions. 

\subsection{Merging Function Calls}\label{sec:merging-calls}
During the merging of a pair of functions, a pair of function calls may be encountered. If this occurs with functions that have not been encountered yet, the functions themselves must be merged in a recursive manner, resulting in an equivalence lemma and a set of mappings between the parameters of the functions. However, in addition to this, the corresponding arguments in the function calls must also be merged together to identify further calls to helper functions and to create further mappings between the parameters of the original functions. Mappings between arguments are created using the mappings between the corresponding function parameters. For example, here are two functions called \dafnyinline{insertSortedM} and \dafnyinline{insertSorted1} that each implement the insertion sort algorithm:
\begin{dafny}[highlightlines={5,14}]
function insertSortedM(insert: List<int>, sorted: List<int>): List<int>
  {
  match insert {
    case Nil => sorted
    case Cons(x, xs) => insertSortedM(xs, insertM(sorted, x))
  }
}

function insertSorted1(sorted: List<int>, insert: List<int>): List<int>
  decreases insert
 {
  match insert {
    case Nil => sorted
    case Cons(x, xs) => insertSorted1(insert1(x, sorted), xs)
  }
}
\end{dafny}
%
These functions rely on helper functions \dafnyinline{insertM} and \dafnyinline{insert1} that each insert a single integer into a sorted list while maintaining its order. Their implementations are in \Cref{sec:intro-background}. Thus, the arguments in the function calls to \dafnyinline{insertSortedM} and \dafnyinline{insertSorted1} must themselves be merged to discover that an equivalence lemma between the helper functions \dafnyinline{insertM} and \dafnyinline{insert1} is necessary (the corresponding lines are highlighted above). This results in the following equivalence lemmas:

\begin{dafny}
lemma equivalenceInsertSorted5(t: int, xs: List<int>)
  ensures (insert1(t, xs) == insertM(xs, t))
{}

lemma equivalenceGo5(insert: List<int>, sorted: List<int>)
  ensures (insertSorted1(sorted, insert) == insertSortedM(insert, sorted))
{
    match insert {
        case Nil => {}
        case Cons(x, xs) => equivalenceInsertSorted5(x, sorted);
    }
}
\end{dafny}
% 

\subsection{Merging Match Expressions}

Merging match expressions is complex, as two match expressions can be equivalent even when they are very different structurally. They can have different numbers of cases, containing different patterns in different orders. For example, below are the functions \dafnyinline{isOdd1} and \dafnyinline{isOdd2}. They each call the functions \dafnyinline{isEven1} and \dafnyinline{isEven2} respectively. These four functions are all implemented in a similar way to the functions \dafnyinline{isOdd}, \dafnyinline{myIsOdd}, \dafnyinline{isEven} and \dafnyinline{myIsEven} respectively in \Cref{sec:mutually-recursive}. However, they instead operate on natural numbers defined using the \dafnyinline{UnaryNat} datatype:
\begin{dafny}
datatype UnaryNat = Zero | Succ(pred: UnaryNat)
\end{dafny}
% 
The functions are as follows:
\begin{dafny}
function isOdd1(un: UnaryNat): bool {
  match un
  case Zero => false 
  case Succ(pred) => isEven1(pred)
}

function isOdd2(un: UnaryNat): bool {
  match un
  case Zero => false 
  case Succ(Zero) => true 
  case Succ(Succ(Zero)) => false 
  case Succ(n) => isEven2(n)
}
\end{dafny}
%
To provide full context, the functions \dafnyinline{isEven1} and \dafnyinline{isEven2} are provided below though they are irrelevant for this example:
\begin{dafny}
function isEven1(un: UnaryNat): bool {
  match un
  case Zero => true
  case Succ(pred) => isOdd1(pred)
}

function isEven2(un: UnaryNat): bool {
  match un
  case Zero => true
  case Succ(pred) => isOdd2(pred)
}
\end{dafny}

The case with the pattern \dafnyinline{Succ(pred)} in the \dafnyinline{isOdd1} function has been expanded to form the last three cases of the \dafnyinline{isOdd2} function. Therefore, the body of the \dafnyinline{Succ(pred)} case (\dafnyinline{isEven1(pred)}) must be merged with each of the bodies of the last three cases (\dafnyinline{true}, \dafnyinline{false} and \dafnyinline{isEven2(n)} respectively). The statements resulting from these merges must then be concatenated to form the body of the \dafnyinline{Succ(pred)} case in the equivalence lemma for the \dafnyinline{isOdd1} and \dafnyinline{isOdd2} functions. This results in the following equivalence lemmas:
\begin{dafny}
lemma equivalenceIsOdd(un: UnaryNat)
  ensures (isOdd1(un) == isOdd2(un))
{
  match un
  case Zero => {}
  case Succ(pred) => equivalenceIsEven(pred);
}

lemma equivalenceIsEven(un: UnaryNat)
  ensures (isEven1(un) == isEven2(un))
{
  match un
  case Zero => {}
  case Succ(pred) => equivalenceIsOdd(pred);
}
\end{dafny}

\section{Type Transformations}\label{sec:type-transformations}

Two functions can have the same purpose even when they operate on different types. These functions are equivalent if the types of one function can be transformed into the types of the other. Such functions cannot be proven equivalent by the Stainless equivalence checker, however, this is possible in EquiDafny. For example, here are the functions \dafnyinline{sumM} and \dafnyinline{sum1}. \dafnyinline{sumM} calculates the sum of a sequence of integers using the inbuilt Dafny sequence type (|seq|). However, \dafnyinline{sum1} calculates the sum of a list of integers using the user-defined data structure provided in \Cref{sec:list-structure}. EquiDafny can prove these functions equivalent if the user provides another function that transforms a Dafny \dafnyinline{seq} into the user-defined \dafnyinline{List}. The following function \dafnyinline{seqToList} is one possible such function:
\begin{dafny}
function seqToList(l: seq<int>): List<int> {
    if |l| == 0 then Nil
    else Cons(l[0], seqToList(l[1..]))
}
\end{dafny}
% 
The implementations of \dafnyinline{sumM} and \dafnyinline{sum1} are provided below. They each use a tail recursive helper function (\dafnyinline{sumAccM} and \dafnyinline{sumAcc1} respectively) to assist in calculating the sum:
\begin{dafny}
function sumM(l: seq<int>): int {
    sumAccM(0, l)
}

function sumAccM(acc: int, l: seq<int>): int
    decreases l
{
    if |l| == 0 then acc
    else sumAccM(acc + l[0], l[1..])
}

function sum1(l: List<int>): int {
    sumAcc1(l, 0)
}

function sumAcc1(l: List<int>, acc: int): int
    decreases l
{
    match l {
        case Nil => acc
        case Cons(h, t) => sumAcc1(t, acc + h)
    }
}
\end{dafny}
% 
Thus, EquiDafny can prove \dafnyinline{sumM} and \dafnyinline{sum1} equivalent by generating the following equivalence lemmas (the lines where the \dafnyinline{seqToList} function is used are highlighted):
\begin{dafny}[highlightlines={2,7}]
lemma equivalenceHelper(acc: int, l: seq<int>)
  ensures sumAccM(acc, l) == sumAcc1(seqToList(l), acc)
  decreases l
{}

lemma equivalence(l: seq<int>)
