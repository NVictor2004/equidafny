The aim of this project is to build a tool on top of the Dafny program verifier that removes as many of the limitations identified in \Cref{sec:audit} as possible. Some of these limitations are out of the scope of this project. Preventing incorrect counterexamples (as described in \Cref{sec:counterexamples}) is one such limitation, as it results from problems in Boogie and the underlying Z3 solver. Similarly, the limitations related to imperative programs (as described in \Cref{sec:imperative-equivalence}) are also out of scope, as Dafny functions provide enough complexity for this project by themselves.

I plan to build my tool in Scala. It will be called from the command line, taking as input multiple Dafny files, containing the functions to be compared and any help the user needs to provide. The tool will also require a JSON configuration file, specifying which functions must be proven to be equivalent and any other information the tool requires. The tool will attempt to create an equivalence proof and prove it using Dafny; Dafny's output will be used as the output of the tool.

The following table summarises the current development plan, broken down into milestones. Each milestone has an associated completion deadline and a description of what that milestone involves. Each milestone is described as either Necessary or Optional. If Necessary milestones take longer than I expected, I will use the time previously dedicated to Optional milestones to complete the Necessary ones.

If I have time remaining once all the project and evaluation milestones are completed, I plan to further extend our tool to handle the remaining limitations relating to Dafny functions identified in \Cref{sec:audit}. This includes removing the necessity for the user to explicitly define induction schemes to prove lemmas (\Cref{sec:induction}) and implementing the ability to prove user-provided auxiliary lemmas (\Cref{sec:auxiliary-lemmas}).

\paragraph{Building the basic structure}\label{para:basic-structure} This milestone involves creating the skeleton of the tool. It should be able to take in Dafny files and a JSON configuration file. The Dafny files will contain the two functions being compared, their associated helper functions and an equivalence lemma without any user assistance. The JSON file will be used to specify which are the main functions to be tested for equivalence. The tool will combine the Dafny files together, call the Dafny verifier on the resulting file, and return its output. Equivalence lemmas with no user assistance are used here to provide an evaluation baseline for the evaluation of the remaining milestones. 

\paragraph{Creating a CI script for Continuous Testing and Evaluation}\label{para:ci-scripts} At each milestone, evaluation data must be generated and collected (see \Cref{sec:evaluation-plan} for more details on this). This milestone involves creating a script to collect this data, and setting up a GitLab CI pipeline to automatically run this script on every merge. Once this is done, evaluation data should be collected for the previous milestone. Then, the equivalence lemmas should be replaced with lemmas that include all the user assistance that Dafny requires, followed by a recollection of the evaluation data, to serve as another baseline for the remaining milestones. 

\paragraph{Create Parser for Dafny functions}\label{para:parser} Several of the future milestones will require an in depth understanding of the structure of the Dafny functions being compared and of the equivalence lemma provided by the user. Therefore, in this milestone, I will create parsers specifically for Dafny functions and lemmas. 

\paragraph{Copying Variants into the Main Lemma}\label{para:variants} As described in \Cref{sec:termination}, when one or both of the functions being compared require the user to explicitly provide variants, this must be copied into the main equivalence lemma. This milestone involves implementing this functionality.

\paragraph{Generating Helper Equivalence Lemmas as Axioms}\label{para:helper-axioms} This milestone will involve implementing the method of finding and generating equivalence lemmas for helper functions described by \textcite{milovancevicProvingDisprovingEquivalence2023} and summarised in \Cref{sec:equivalence-lemmas}. For now, these lemmas will be generated as axioms; they will be proven properly in a later milestone. 

\paragraph{Calling Helper Lemmas in the Main Lemma}\label{para:calling-lemmas-main} As described in \Cref{sec:equivalence-lemmas,sec:termination}, helper equivalence and termination lemmas must be explicitly called in the main equivalence lemma, under the correct conditions and with the correct arguments. This milestone involves implementing this specifically for the main equivalence lemma.

\paragraph{Calling Helper Lemmas in Equivalence Lemmas}\label{para:calling-lemmas-helper} This milestone involves extending the functionality implemented in the previous milestone to also prove the generated helper equivalence lemmas.

\paragraph{Proving Equivalence with one of a number of solutions}\label{para:multiple-solutions} In certain cases, including those described by \textcite{milovancevicProvingDisprovingEquivalence2023}, the user may wish to prove the equivalence of a function with any one of a number of possible other functions. This milestone involves implementing this.

\paragraph{Allowing the user to provide Auxiliary Lemmas as Axioms}\label{para:auxiliary-axioms} In certain cases, the user will need to provide auxiliary lemmas to help Dafny prove equivalence. These lemmas are specific to each individual scenario, and so automatic generation is out of scope for this project. Therefore, a reasonable alterative is to allow the user to provide auxiliary lemmas, which can then be called in the main equivalence lemma. These auxiliary lemmas will be added as axioms, as it would be difficult to prove them automatically. The burden of ensuring these lemmas are correct will be on the user. This milestone will involve implementing this.

\paragraph{Proving equivalence of higher order functions}\label{para:higher-order} When proving the equivalence of functions that output lambda functions, these functions are equivalent if the lambda functions output the same values for the same inputs. This can be proven through a universal quantification over the domain of the lambda functions. This milestone involves implementing this functionality. 

\paragraph{Writing the Final Report}\label{para:final-report-project} Throughout development, I will add to the Final Report as I go along; this milestone involves completing the technical and evaluation chapters in it.

\paragraph{Creating Initial Evaluation Testsuite}\label{para:init-eval-testsuite} Before evaluation can begin, we need a testsuite containing pairs of functions which our tool will attempt to prove equivalent. As described in \Cref{sec:audit}, I have already created an initial testsuite using the equivalence tests from the repository for the Stainless Scala verification tool\cite{StainlessFrontendsBenchmarks}. This testsuite will be extended in a later milestone. 

\paragraph{Setup of Evaluation Data Gathering}\label{para:evaluation-data-gathering} As described in \Cref{sec:project-plan}, once each milestone is completed, a CI script will be used to automatically collect evaluation data. The first two milestones will provide baseline data on Dafny without any user assistance, and on Dafny with all the assistance it requires respectively. Data collected from all subsequent milestones will be compared to this baseline data. The evaluation data will consist of two categories. First, we must gather data to represent how difficult each example is for Dafny to verify. This category will include the metrics of the number of lines of code in each function being compared, the number of helper functions called and the time taken for Dafny to verify the example. Second, we must gather data to represent how much user assistance Dafny requires. This will include the metrics of the number of lines of code in the main equivalence lemma and the numbers of helper equivalence and auxiliary lemmas the user needs to provide. The aim of this project is for the metrics in the second category to decrease as much as possible. The first category metrics will ensure that we are interpreting these decreases in the correct context. These metrics are too shallow to provide a complete picture of the complexity of the examples and the level of user assistance required, however, they will provide a reasonable approximation. 

\paragraph{Testsuite Development}\label{para:testsuite-development} A second set of program equivalence tests have been gathered by \textcite{badihiEqBenchDatasetEquivalent2021}. This milestone involves converting these tests from C and Java into Dafny, and appending them into my evaluation testsuite.

\paragraph{Benchmark Comparison}\label{para:benchmark-comparison} In this milestone, I will compare the results of our tool on our evaluation testsuite with the results from the original Dafny verifier, to demonstrate the improvements made. I will also compare our tool with Stainless on the subset of our testsuite that originated from their equivalence tests, to demonstrate how our tool compares with other state-of-the-art program verifiers.
