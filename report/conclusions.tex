\chapter{Conclusions and Future Work}

\section{Achievements and Limitations}

The aim of this project was to minimise the level of user assistance required to create program equivalence proofs. We achieved this by implementing EquiDafny, an equivalence checker on top of Dafny. In particular, here are the main contributions of the project:

\footnote{Make sure this list is the same as the one in the introduction}
\begin{itemize}
    \item \nameref{sec:literature-review}: Described the current state-of-the-art tools for proving program equivalence
    \item \nameref{sec:audit}: Explored Dafny's capabilities in proving program equivalence between Dafny functions
    \item Dataset of Equivalence tests: Created a dataset of pairs of equivalent Dafny functions
    \item \nameref{chp:design}: Development of the function merging algorithm to automatically generate equivalence lemmas and to address the challenges the Dafny verifier faces 
    \item \nameref{chp:implementation}: Implemented EquiDafny: a command-line tool on top of the Dafny verifier
    \item \nameref{chp:evaluation}: Evaluated EquiDafny against the Dafny verifier and the Stainless equivalence checker
\end{itemize}

Out of the 91 tests in my dataset of equivalence tests, the base Dafny verifier can verify 25 tests while EquiDafny can verify 56 tests. Thus, EquiDafny presents a substantial improvement over the base Dafny verifier. The tool can verify these tests in only around 1.5 seconds on average. EquiDafny can also verify three tests that Stainless fails to verify. Therefore, EquiDafny has great potential to become a performant equivalence checker for Dafny functions. 

However, despite EquiDafny's achievements, the tool has many limitations. An important assumption that EquiDafny makes is that, when expressions are equivalent and have the same structure, their sub-expressions must also be equivalent. However, this is not true in general. EquiDafny also relies on a series of translation rules to convert expressions into the same structure so that they can be merged together. Some of my tests require complex translations that have not been implemented yet, restricting EquiDafny's effectiveness. 

\section{Future Work}\label{sec:future-work}

There is great scope for extending EquiDafny in the future. Some suggestions are listed below. 

\subsection{Algorithm extensions}

These suggestions involve increasing the effectiveness of the function merging algorithm. 

\paragraph{Addressing Evaluation limitations} In \Cref{sec:eval-limitations}, I describe several limitations of the Function Merging algorithm. Many of these limitations can be addressed by adding features to EquiDafny's implementation, including match expression flattening and variable inlining. 

\paragraph{Automatic auxiliary lemma generation} The evaluation testsuite contains several tests which EquiDafny is unable to prove since they require auxiliary lemmas. These lemmas also need to be called with the correct arguments and under the correct conditions. These lemmas and corresponding calls could be automatically generated, removing the current necessity for users to write and provide their own auxiliary lemmas.

\subsection{Extensions to EquiDafny's scope}

Currently, EquiDafny is only able to generate equivalence lemmas, specifically for Dafny functions. EquiDafny can be extended beyond this.

\paragraph{Improving counter example generation} As described in \Cref{sec:counterexamples}, Dafny counterexamples can be unnecessarily complex and are sometimes inaccurate. These counterexamples could be processed before being presented to the user to check that they are valid and to simplify them whenever possible.

\paragraph{Proving equivalence of imperative methods} As described in \Cref{sec:imperative-equivalence}, imperative methods cannot be proven equivalent using lemmas. Instead, the methods can be proven equivalent by combining them to create a product program and proving postconditions on this program. These product programs can be generated automatically. However, for these programs to be verifiable, they often require complicated invariants that are difficult to generate. Thus, these should be provided by the user and copied into the generated product program.

\subsection{Further extensions}

These extensions will improve EquiDafny and its evaluation testsuite as a whole. 

\paragraph{Evaluation testsuite extension} Currently, I have converted only a small proportion of the EqBench dataset~\parencite{badihiEqBenchDatasetEquivalent2021} into Dafny to form some of the equivalence tests in EquiDafny's evaluation testsuite. The remaining tests can be converted to increase the size and coverage of the testsuite.

\paragraph{Formal verification of optimisation translations} EquiDafny's Optimisation component contains several translations to convert function bodies into simpler structures to increase the effectiveness of the function merging algorithm. However, these translations have not been formally proven to be sound. This could be proven to ensure that EquiDafny's implementation is mathematically robust.

\paragraph{Parser Optimisation} As described in \Cref{sec:system-profiling}, EquiDafny's parsing component consumes a significant amount of time and memory. This can be decreased by using a parser generator (such as ANTLR~\parencite{DefinitiveANTLR4}) instead of the Parsley parser combinator library~\parencite{willisJmie6Parsley2026}, though such a change has other drawbacks that should be considered. It is important to note that the majority of the overall time taken will still be spent during the final Dafny verification component, thus optimising the parser will only improve overall performance slightly.
