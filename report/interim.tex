\section{Dafny}

As described in \textcite{leinoDafnyAutomaticProgram2010}, Dafny is primarily a programming language, containing many of the classic language features and constructs we expect from a modern programming language. However, in addition to this, it includes specification constructs, such as preconditions, postconditions and loop invariants, to allow Dafny's program verifier to automatically prove that a given program matches its specification. Dafny can also be compiled into a variety of other languages, including C\#, Java and Python, allowing verified programs to be integrated easily into existing codebases.

Dafny's program verification heavily relies on Boogie \parencite{10.1007/11804192_17}, another state-of-the-art program verifier. The verification process involves translating a Dafny program into a Boogie program; this is then translated into a series of verification conditions, which are passed to the Z3 SMT solver \parencite{10.1007/978-3-540-78800-3_24}. 

\subsection{Dafny Example}

To demonstrate Dafny's capabilities in proving program equivalence, consider the following example, converted from the original Scala provided by \textcite{milovancevicProvingDisprovingEquivalence2023}. These two examples attempt to check whether a list is sorted. The first is as follows, involving a helper function \lstinline|loop| and the main function \lstinline|isSortedR|:

\begin{lstlisting}
function loop(p: int, l: seq<int>): bool
  decreases l
{
  if |l| == 0 then true
  else p <= l[0] && loop(l[0], l[1..])
}

function isSortedR(l: seq<int>): bool
{
  if |l| == 0 then true
  else loop(l[0], l[1..])
}
\end{lstlisting}
%
The second is as follows:
\begin{lstlisting}
function isSortedB(l: seq<int>): bool
  decreases |l|
{
  if |l| == 0 then true
  else if |l| == 1 then isSortedB([])
  else l[0] <= l[1] && isSortedB(l[1..])
}
\end{lstlisting}
%
To prove the equivalence of these two functions, we can define the following lemma:
\begin{lstlisting}
lemma isSortedEquivalence(l: seq<int>)
  ensures isSortedR(l) == isSortedB(l)
{}
\end{lstlisting}
%
For this example, Dafny is able to verify that these functions are equivalent. Therefore, Dafny is capable of proving the equivalence of simple functions, with very little effort on the user's part.

SymDiff is a differential program verifier \parencite{lahiriSYMDIFFLanguageAgnosticSemantic2012}: it works by specifying the differences between multiple programs and verifying properties about them.

SymDiff can also be used to prove program equivalence however, as described in \textcite{lahiriAutomatedDifferentialProgramb}, it can also be used in Approximate computing, to trade off the accuracy of a program (in an acceptable manner) for improvements in performance or energy consumption. \textcite{lahiriAutomatedDifferentialProgramb} focusses on formally proving control flow equivalence under given differences, by constructing a product program, using the concept of a mutual summary, and passing it to the Boogie program verifier.

An example is as follows:

function leq(cur: int, next: int): bool
{
  cur < next

function iter(l: List<int>): bool
{
  match l
  case Nil => true
  case Cons(x, Nil) => true
  case Cons(x, Cons(y, ys)) => leq(x, y) && iter(Cons(y, ys))

function isSortedA(l: List<int>): bool
{
  match l
  case Nil => true
  case Cons(_, Nil) => true
  case Cons(x, Cons(y, ys)) => x <= y && iter(Cons(y, ys))
}
\end{lstlisting}

This solution is non-equivalent to the reference solution, as it uses a strictly less-than comparison in the \lstinline|leq| function, when it should use a less-than-or-equal-to comparison. Therefore, Dafny is unable to prove the following equivalence lemma:
\begin{lstlisting}
lemma isSortedEquivalence(l: List<int>)
  ensures isSortedA(l) == isSortedR(l)
{}
\end{lstlisting}
%
However, it incorrectly provides \lstinline|Cons(-38, Cons(7681, Nil))| as a counterexample. I extended the above proof to include and use a helper lemma, as shown below:
\begin{lstlisting}
lemma isSortedEquivalenceHelper(x: int, xs: List<int>)
  decreases xs
  ensures iter(Cons(x, xs)) == loop(x, xs)
{}

lemma isSortedEquivalence(l: List<int>)
  ensures isSortedA(l) == isSortedR(l)
{
  match l
  case Nil => {}
  case Cons(x, Nil) => {}
  case Cons(x, Cons(y, ys)) => isSortedEquivalenceHelper(y, ys);
}
\end{lstlisting}
%
Now, Dafny is able to provide a correct counterexample of \lstinline|x = 8855| and \lstinline|xs = Cons(8855, Nil)| for the helper lemma. However, this is not the simplest counterexample possible, as \lstinline|x = 0| and \lstinline|xs = Cons(0, Nil)| would be sufficient.

Finally, as with \hyperlink{ega}{Student A's solution}, Dafny can sometimes provide incorrect counterexamples for non-equivalent functions. When provided with helper lemmas, the tool will eventually provide a correct counterexample, but not necessarily the simplest one.

As asserted by \textcite{putrueleMaskDToolMeasuring2022}, since there are multiple translations steps between the Dafny source code and the verification conditions sent to the Z3 SMT solver, the counterexamples produced by it can be difficult to read and understand. They also note these counterexamples may sometimes be incorrect, as seen in \hyperlink{ega}{Student A's solution}, due to the Z3 solver being incomplete.

function chk(l: List<int>, p: int, a: bool): bool

This example is equivalent to the reference solution, however, Dafny requires a helper lemma to prove this:
\begin{lstlisting}
lemma isSortedEquivalenceHelper(x: int, xs: List<int>)
  decreases xs
  ensures chk(xs, x, true) == loop(x, xs)
{}

lemma isSortedEquivalence(l: List<int>)
  ensures isSortedC(l) == isSortedR(l)
{
  match l
  case Nil => {}
  case Cons(x, xs) => isSortedEquivalenceHelper(x, xs);
}
\end{lstlisting}

However, as with \hyperlink{egc}{Student C's solution}, Dafny requires additional helper lemmas to be provided to prove the equivalence of helper functions. It also requires that these helper lemmas are explicitly called within the main equivalence lemma. 

\textcite{milovancevicProvingDisprovingEquivalence2023} solved this problem by preprocessing the student and reference solutions to find functions with compatible signatures: where the arguments of one function can be permuted so that their types match the types of the arguments of another function. Once candidate pairs of functions are found, equivalence lemmas can be automatically generated and proven. If multiple functions share the same signature, test cases are used to narrow down the search space. These can be defined by the user or generated from counterexamples found when disproving equivalence of other incorrect candidate submissions.
